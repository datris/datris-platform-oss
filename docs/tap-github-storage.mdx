---
title: "GitHub Script Storage"
description: "Store tap Python scripts in a GitHub repository — real commits, PR review, and editing from your own IDE"
---

By default, tap scripts live in Datris's built-in object storage. You can instead connect a
GitHub repository per environment: every script save becomes a commit, runs are pinned to the
exact commit they were saved at, and your team can review, blame, and edit tap code with normal
git tooling.

<Note>
Repository storage is **opt-in** and coexists with built-in storage. Existing taps stay where
they are until you move them; you can run a mix of both indefinitely, and move any tap back to
built-in storage at any time.
</Note>

## What you get

- **A commit per save** — from the tap wizard, the Assistant, or the API. Commit messages are
  templated (e.g. `tap(weather-forecast): update via Datris`).
- **Runs pinned to a commit** — a scheduled run executes exactly the version that was saved,
  served from a local cache, so cron runs make no GitHub API calls and keep working if GitHub
  is unreachable. The local copy is used only when the recorded commit is a commit SHA.
- **External editing** — commit changes from your IDE; Datris detects the drift when the tap is
  opened and offers to load the latest version.
- **Conflict protection** — if the script changed in the repository after you opened it, saving
  is rejected with a clear message instead of silently overwriting.

## Setup

### 1. Create (or pick) a repository

Any repository works — private is typical. Scripts are written to
`<path prefix><tap-name>.py` (default `taps/<tap-name>.py`) on the branch you configure.

### 2. Create a fine-grained personal access token

A PAT is created under a GitHub **user account** and scoped to repositories — you don't add it
to the repository itself. Datris needs **Contents: Read and write** on just the one repo:

1. On GitHub, click your avatar → **Settings** → **Developer settings** (bottom of the left
   sidebar) → **Personal access tokens** → **Fine-grained tokens** → **Generate new token**.
2. Set a name and an expiration.
3. **Resource owner**: pick the user or organization that owns the target repository.
4. **Repository access**: choose *Only select repositories* and pick the repo.
5. Under **Permissions → Repository permissions**, set **Contents: Read and write**
   (**Metadata: Read** is added automatically as a mandatory permission).
6. Generate the token and copy it immediately — GitHub shows it only once.

<Warning>
**For organization-owned repositories**: the org must allow fine-grained PATs under org
**Settings → Third-party Access → Personal access tokens**, and some orgs require each token to
be approved. If the connection test fails with an access error on an org repo, this is the
first thing to check.
</Warning>

<Note>
Fine-grained PATs **always expire**. When the token lapses, saves and non-cached reads for
repository-backed taps fail until you update the secret with a fresh token. Put the expiry
date somewhere you'll see it.
</Note>

### 3. Connect it in Datris

In **Configuration → Code Repository**:

1. Enter the repository (`owner/repo`), branch, and path prefix.
2. Under **Token secret**, click **Create one**, name it (e.g. `github`), and paste the token.
   This stores it in the secrets store with the shape Datris expects — a `token` field, tagged
   `_type=repo_token`.
3. Click **Test connection** — it verifies the token can reach the repository, has push
   access, and that the branch exists.
4. Check **Enable repository storage** and **Save**. Saving re-validates the connection.

Once enabled, **new** tap scripts default to the repository — including taps the Assistant
builds. Existing taps are never moved automatically.

<Tip>
Creating the token secret manually in the Secrets tab also works, but two details matter: the
field holding the PAT must be named `token`, and the secret must be tagged `_type=repo_token`
or it won't appear in the Token secret dropdown. The **Create one** flow handles both.
</Tip>

### GitHub Enterprise Server

Set **API base URL** to your instance's API endpoint (e.g. `https://ghes.example.com/api/v3`).
Leave it at `https://api.github.com` for github.com.

## Day-to-day behavior

| Action | What happens in the repository |
|---|---|
| Save a script (wizard, Assistant, or API) | A commit on the configured branch; the tap pins to that commit |
| Run a tap (manual or cron) | Nothing — the pinned commit is read from a local cache |
| Edit the file directly in GitHub | Opening the tap loads the repository's latest version into the editor, with a banner explaining that runs keep the previously saved version until you test and save |
| Save when the file changed externally | Rejected with a conflict message — pull the latest, reapply your edits, save again |
| Delete the tap | A delete commit removes the tap's own script file (`<path prefix><tap-name>.py`) from the branch head when no other tap uses it; **git history is preserved**. Any other file is left in place with a warning (see [Which file a tap owns](#which-file-a-tap-owns)) |
| Save a pipeline with an AI rule or AI transformation | A commit per script under `pipelines/<pipeline>/`; runs pin to it (see [Pipeline scripts](#pipeline-scripts)) |

Run history records the commit SHA each run executed, so any run can be traced to the exact
script version in your repository.

## Moving taps between backends

In the **Taps** list, each row shows a **GitHub** badge when its script is repository-backed.
The cloud action on the row moves a tap's script in either direction:

- **Move to GitHub** — commits the current script to the repository and re-points the tap.
- **Move to built-in storage** — copies the script back to object storage. The repository file
  is left in place (remove it manually if you want it gone).

Both directions are recorded as a new tap version, so the move itself is auditable and
reversible.

A move to GitHub writes the tap's own path, `<path prefix><tap-name>.py`. If another tap already
runs its script from that file, the move is refused with `409` and nothing is written; the other
tap's script is never replaced. The same holds for a script stored for a new tap name: pick another
name, or move the other tap first.

A tap that already stores its script at its own path keeps storing it there, even while another tap
also runs from that file, for an administrator, an editor without catalog limits or an unrestricted
API key. A user limited to catalogs, or an API key whose tap access is limited (it cannot read every
tap, or its `tap:update` is limited to a catalog or to what it created), is refused that upload, with
nothing written, when another tap's current script is the same file in any spelling of its path: the
answer is the one above (`403` naming `tap:read` for a key limited to a catalog or to what it
created, `404` for a user limited to catalogs, the `409` for a key that reads every tap), and the
refusal is recorded in the audit log. When the list of taps cannot be read, such an upload answers
`503` and nothing is written. To keep editing such a tap, an administrator gives it its own file
(move the other tap's script to built-in storage and back, or store a copy for it under its own name).

## Which file a tap owns

Deleting a tap, removing its old script versions, and the first script stored under a tap name
(or a move into the repository) only ever touch the script file that belongs to that tap:

- **Built-in storage:** the object the platform wrote for the tap (`tap-scripts/<tap-name>_<id>.py`).
- **Code repository:** `<path prefix><tap-name>.py`, under the current path prefix or one of the
  repository's **earlier path prefixes** (below). A file in the prefix's `pipelines/` folder is never
  a tap's own file.

A tap whose stored repository file is not its own (a path placed by hand, or an earlier prefix that
is not recorded) is the one exception, in this release: a script upload for it by an administrator,
an editor without catalog limits or an unrestricted API key is still written to that stored file,
and the same upload by a user limited to catalogs or a key whose tap access is limited is refused
(see below).

**Deleting a tap** deletes its own script file only when no other tap uses the same file. Otherwise
the file is left in place, the tap is still deleted, and the delete response's `warnings` says: "The
tap's script file was left in place because it is not a file this tap alone owns; remove it by hand
if it is no longer wanted." That happens for a tap pointed at a file by hand, a tap stored under a
path prefix that is not recorded, and two taps sharing one script (deleting either one no longer
removes the script the other still runs). Removing old script versions follows the same rule: only
the tap's own older objects that no tap uses are removed. When the list of taps cannot be read, the
tap is deleted and its file is kept with the same warning, and the server log says so.

On built-in storage, a script object the platform wrote under another name (a tap created in the
wizard and renamed before its first save, or a script generated before the tap had its name) is
removed with the tap, and with its old script versions, when no tap has that other name and no
other tap uses the object. Otherwise it is kept with the same warning.

**Earlier path prefixes.** Changing the **path prefix** in the settings records the previous prefix
in the repository configuration's `earlierPathPrefixes` list, so taps already stored under it keep
being treated as their own files. If you changed the prefix before this was recorded, add the old
prefix to `earlierPathPrefixes` with `PUT /api/v1/code-repo` (needs `code-repo:write`; send the
whole configuration with the list). A save that leaves the list out keeps the stored list. There is
no field for it in the settings page.

A tap whose stored script file is not its own still runs and saves as before in this release. A
script upload for it by an administrator, an editor without catalog limits or an unrestricted API
key is still written to its stored file. The same upload by a user limited to catalogs, or by an
API key whose tap access is limited (it cannot read every tap, or its `tap:update` is limited to a
catalog or to what it created), is refused with `409` and nothing is written; the message names only
that tap and asks an administrator to move the script to the tap's own path. When the code
repository settings cannot be read, such an upload is answered `503` and nothing is written. A key
limited only for pipelines, whose tap capabilities carry no catalog or owner limit, uploads as
before.
`datris doctor` lists such taps under [`tap.references`](/doctor#the-checks); in a later release
the next script stored for such a tap is written to its own path and the tap is pointed at it,
leaving the earlier file in place. To give such a tap its own file now, record the earlier prefix
(if that is the cause) or move the tap's script to built-in storage and back.

A catalog restore into an install that stores tap scripts in a code repository follows the same
rule as a first upload: a restored tap whose live copy has no repository file of its own (it is
new here, or on built-in storage) is not written over a file another tap runs from. The restore
reports it as a clash, with the restored tap's name and file, and nothing is restored. For a user
limited to catalogs or a key whose tap access is limited, the clash says only that the file cannot
be written by this restore.

The same restore by a user limited to catalogs or a key whose tap access is limited also follows
the upload rule above: when a restored tap's live copy is stored in the repository at a file that is
not its own, the restore lists that tap as a clash, naming only the tap and asking an administrator
to move its script to the tap's own path, records the refusal in the audit log, and restores
nothing. Such a restore is refused the same way, with the held wording above and an audit row, when a
restored tap's live copy is stored at its own file and another tap also runs its script from that
file. A tap the caller may not write at all is not judged by these checks: it is listed under
`failed` with its scope refusal and the rest of the archive is restored. Other callers' restores are
unchanged.

## Pipeline scripts

The Python scripts behind a pipeline's [AI data-quality rule](/data-quality/ai-rules) and
[AI transformation](/transformation/ai-transformation) use the same repository. With repository
storage enabled, the script generated for a new pipeline (or for a pipeline that has no script
yet) is committed instead of going to built-in storage.

**Path layout.** Each pipeline gets a folder under the configured path prefix, on the configured
branch. With the default prefix `taps/`:

```
taps/pipelines/<pipeline>/data-quality.py
taps/pipelines/<pipeline>/transformation.py
```

Tap files (`taps/<tap>.py`) are untouched, and the token needs no new permission.

**Commit messages.** `{name}` is `<pipeline>/<kind>` (`orders/dataQuality`,
`orders/transformation`), `{action}` is `create`, `update` or `delete`, and `{user}` is the label
of the API key that saved the pipeline, or `datris` when there is none (the script was generated during a run, or saved from a UI session without an API key).
With the default template (or an empty one) pipeline scripts use
`pipeline({name}): {action} via Datris`, for example `pipeline(orders/transformation): update via Datris`.
A custom template is applied as written, so a template written for taps (for example one starting
`tap(`) also prefixes pipeline commits that way.

**Pinned runs.** The pipeline records the commit SHA of each script. Runs read that commit from
the local cache, so a run makes no repository call once the commit is cached, and the run's
status line names the short SHA ("Running stored CodeGen script generated at … (code repository
commit abc1234)"). `GET /api/v1/pipelines/{name}/codegen-scripts` returns `storage: "github"`,
`repoPath` and `commitSha` for each script.

**Editing in the repository.** Runs stay on the recorded commit after an edit in GitHub. The
read endpoint then reports `drift: true` with the branch-head `headSha`, and for the transformation script the Columns section
of the [lineage panel](/provenance#column-level-lineage) shows "Changed in the repository" with a
**Load latest** action. To adopt the edit, call
`POST /api/v1/pipelines/{name}/codegen-scripts/{kind}/pull` (needs `pipeline:update`); it records
the head commit and makes no commit of its own. Later saves keep the adopted edit while the
instruction and source schema are unchanged.

**Conflicts.** When the instruction or schema changes, the save regenerates the script and commits
it on top of the recorded commit. If the file was edited in the repository since then, the commit
is rejected: the pipeline is saved, the script and its recorded commit are unchanged, and the save
response carries a warning naming the two ways forward: pull the edit, or replace it with
`POST /api/v1/pipelines/{name}/codegen-scripts/{kind}/regenerate?overwrite=true`. A forced regenerate
without `overwrite=true` is rejected the same way (409). A hand edit is never overwritten silently;
an overwritten edit stays in the repository history.

Until the conflict is resolved, runs keep executing the recorded commit, without the new instruction
or schema and with no model call. The run's status line names the commit and says to pull or
regenerate with `overwrite=true`, and the read endpoint shows `conflict: true` with the
`conflictReason`. Saving the same configuration again makes no model call and repeats the warning.
Pull or a regenerate with `overwrite=true` clears the conflict. A run that meets the same conflict
(for example after a version restore) records it the same way and runs the recorded commit.

**Moving a script.** An existing script keeps its storage on every save. To move one, call
regenerate with `storage=github` or `storage=builtin`; the old copy is left in place. Scripts that
existed before repository storage was enabled stay in built-in storage until you move them.

Leftover copies are not tracked. Deleting the pipeline removes only the copies its scripts point at
now, so files and objects left behind by earlier moves stay until you remove them. Moving a script
back to the repository writes over a leftover file at the same path without a conflict check, and
the commit is labelled `create`.

**When the repository is unreachable or the token has expired:**

- At save, the pipeline is saved and the script is pending with the reason; the save response
  carries a warning. The first run after the repository is back generates and commits it.
- A run whose recorded commit is cached is unaffected.
- A run whose commit is not cached (the cache does not survive an image rebuild) fails with
  "Code repository is unreachable and no cached copy … exists locally". It does not fall back to
  generating a different script.
- A run that generates a pending script and cannot commit it runs the generated script, logs a
  warning, and the script stays pending.

If repository storage is disabled while scripts point at it, their runs fail with "This pipeline's
CodeGen script is stored in a code repository, but no enabled repository is configured"; re-enable
the repository, or regenerate with `storage=builtin` to move the script back to built-in storage.

**Delete.** Deleting the pipeline (or a catalog together with its items) makes a delete commit per
script file that is unchanged since its recorded commit; git history is kept. A file that was edited
in the repository since then is kept: a hand edit is never removed by Datris. The pipeline and its
script records are still deleted, and the delete response's `warnings` names each kept file so you
can remove it by hand if it is no longer wanted. When the repository cannot be reached the files are
kept the same way, with a warning, and the delete still goes ahead. If the delete request itself fails
(for example it times out), the warning says the delete could not be confirmed: check the repository
and remove the file by hand if it is still there. Deleting a tap whose script is in
the repository follows the same rule, and also leaves in place a file that is not the tap's own (see
[Which file a tap owns](#which-file-a-tap-owns)). Saving a pipeline without an AI instruction it had before
removes that script the same way: an edited file is kept and named in the save response's `warnings`.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Token secret dropdown is empty | The secret isn't tagged `_type=repo_token` — recreate it via **Create one** |
| Test connection: token rejected | Token expired or revoked — generate a new PAT and update the secret |
| Test connection: cannot push | Token is missing **Contents: Read and write** on this repository |
| Test connection: access error on an org repo | Org policy blocks fine-grained PATs, the token awaits approval, or SSO authorization is required |
| New taps still land in built-in storage | **Enable repository storage** isn't checked and saved |
| Scheduled runs keep working while GitHub is down | Expected — runs read the pinned commit from the local cache |
| Tap delete warns that the script file "was left in place" | The tap's script file is not one it alone owns: another tap uses it, it was placed by hand, or it is under an unrecorded earlier path prefix (see [Which file a tap owns](#which-file-a-tap-owns)) |
| Storing a tap's script or moving it to GitHub returns `409` saying another tap runs its script from that file | Another tap runs its script from `<path prefix><tap-name>.py`; use another tap name. For a user or key with limited tap access the same refusal also applies to a tap that already stores its script there; an administrator gives each tap its own file |
| Pipeline save warns that a script "changed in the code repository" | The script file was edited in GitHub — pull the edit, or regenerate with `overwrite=true` (see [Pipeline scripts](#pipeline-scripts)) |
