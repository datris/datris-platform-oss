title: "API Keys"
description: "Enable API-key authentication for the UI, CLI, MCP clients, and any other programmatic access to Datris."
---

By default, the Datris OSS install accepts unauthenticated requests on the REST and MCP APIs — fine for laptop development, wrong for any shared or hosted setup. Turn on API-key authentication and every caller (the UI, the CLI, agent MCP clients) must present a key that the platform recognizes.

This page covers single-tenant deployments. Multi-tenant setups (`MULTI_TENANT=true`) use the same flag and a different mapping mechanism — see [Multi-tenant](#multi-tenant) below.

## What it does

When `USE_API_KEYS=true`:

- Programmatic clients (CLI, MCP-connected agents, external scripts) must include `x-api-key: <value>` on every request.
- The platform validates the value against a known set of issued keys.
- The capability framework enforces what each scoped key is allowed to do (see [the capability model](#the-capability-model)). Calls outside the key's scope return HTTP 403. A key limited to a catalog or to what it created is held to that limit on every route, reads included (see [Keys limited to a catalog or to what they created](#keys-limited-to-a-catalog-or-to-what-they-created)).
- The Datris UI behavior depends on whether [user authentication](/user-auth) is also enabled. With `USE_USER_AUTH=true` (recommended), the UI authenticates via session cookie alone — no API key is sent or required. With user-auth off, the UI falls back to the legacy "paste a key" prompt on first load.

The flag is independent of `USE_USER_AUTH` but they're paired conceptually — see [the supported matrix](#supported-configurations) below.

## Enabling it

The recommended setup pairs `USE_API_KEYS=true` with `USE_USER_AUTH=true` (see [the matrix below](#supported-configurations) for why).

### 1. Flip the flags

In `.env`:

```bash
USE_USER_AUTH=true
USE_API_KEYS=true
```

### 2. Restart

```bash
docker compose up -d --force-recreate datris
```

### 3. Use the platform

- **The UI**: log in with your admin account. The session cookie authenticates browser flows — no `x-api-key` is sent, no Connect prompt appears. The Assistant inherits your session for capability checks; its tool calls, version-history entries, and [audit log](/audit-log) records are attributed to you (`session:<your username>`), not to the platform's internal `ui` key.
- **Programmatic clients** (CLI, MCP agents, scripts): each one needs its own key, issued from **Configuration → API-Keys**. See [the issuance flow](#issuing-keys-for-cli-mcp-and-other-clients) below.
- **Tap scripts** reading platform data need nothing: each run gets a short-lived, read-only token that the tap wrapper attaches automatically (see [Taps → Querying Datris Data](/taps#querying-datris-data)). The token reads platform data and nothing else; the in-platform chat endpoints refuse it.

That's it. No env var to track, no value to paste anywhere.

### Legacy mode (`USE_USER_AUTH=false`, `USE_API_KEYS=true`)

If you can't or don't want to enable user-auth, the UI falls back to the older "paste a key" flow:

- The Connect prompt appears on first load
- The default seeded value is `default-ui-key` (defined in `docker/vault-init.sh`); paste it once
- Browser stores it in localStorage; subsequent loads skip the prompt
- Rotate it any time from **Configuration → API-Keys → ui → Rotate** (the new value is mirrored automatically into the validation map, and the operator distributes it out of band)

This mode is fine for laptop development but **not** appropriate for shared installs — anyone with the URL can reach the Connect prompt, and the only gate is knowledge of the pasted value.

## Issuing keys for CLI, MCP, and other clients

Open **Configuration → API-Keys → Issue new key**.

1. Pick a label (`cli`, `claude-desktop`, `cursor`, `prod-loader`, etc.) — lowercase, hyphens/underscores ok.
2. Pick a template or build a capability list manually:
   - **read-only** — observer access to pipelines/taps/jobs/metadata + query/search
   - **rag-builder** — create pipelines and taps in any catalog, upload documents into, and feed by its taps, only the pipelines it created, run vector search across all collections, run the taps it created, and read and write only tap secrets
   - **reporting** — analyst-shaped read access
   - **ops** — run any tap, monitor and kill jobs, read pipelines and taps; no uploads, no edits
   - **full-access** — legacy `*:*` shape; avoid for agents
3. Review and create.
4. **Copy the value immediately** — it's shown once. The value lives in Vault (`oss/api-keys`) and is never returned by the API again after this modal closes.
5. Paste the value into the agent's MCP client config (or CLI env var, etc.).

Each label is a distinct identity in the [audit log](/audit-log) and can be revoked independently of the others. Every issued key also gets a stable id (shown in the audit log) so a label that is revoked and later re-issued is not confused with its predecessor.

<Note>
The Vault label `ui` is reserved for the seeded fallback UI key (used in legacy `USE_USER_AUTH=false` mode, and for the in-platform chats' internal MCP-to-REST hop on behalf of logged-in users, where each call is narrowed to that user's role (see [User Authentication](/user-auth#roles-in-the-chats)), and full-access keys; any other key's chat tool calls use that key itself). You don't issue this one from the UI — it's seeded by `vault-init.sh` on first boot and rotated from the API-Keys tab like any other key.
</Note>

## Supported configurations

`USE_API_KEYS` and `USE_USER_AUTH` compose into four states:

| `USE_USER_AUTH` | `USE_API_KEYS` | Behavior |
|---|---|---|
| `false` | `false` | Full anonymous. No prompts, no auth, no gating. **OSS default; fine for laptop dev.** |
| `true` | `true` | UI gated by login; programmatic clients gated by key. **Recommended for shared installs.** |
| `true` | `false` | UI gated by login; programmatic clients are anonymous. Workable, slightly odd. |
| `false` | `true` | **Not recommended.** No coherent auth mechanism for the browser. Pick a different combination. |

The fourth row is the trap. When you require strict auth for programmatic clients but no login for the UI, the browser has nothing to present. API keys are intended to be used alongside user auth — set both flags together, or neither.

## Rotating a key

From the **API-Keys** tab in Configuration, click **Rotate** on any row:

1. A new value is generated server-side
2. The validation map (`oss/api-keys`) and operator-facing record are updated in sync
3. The new value is shown once in a copy-to-clipboard modal
4. Distribute the new value out of band to whoever was using it; they'll get 401s on their next request and need the new value

The previous value stops working the moment Rotate returns.

## Revoking a key

From the **API-Keys** tab, click **Revoke**. The key's metadata is marked revoked; the underlying value stays in `oss/api-keys` so failed auth attempts log as "revoked key" rather than "unknown key" — useful for tracking compromised credential reuse.

A revoked key is rejected with `401 {"error":"API key is revoked or invalid"}` on every authenticated route, and the denial is recorded in the audit log as a security event whose actor is the revoked key's label (an unknown key value is recorded as `unknown-key`, never the value itself). If the secret store itself cannot be read, keys are not resolved at all and the response is `503` rather than falling back to full access.

Revoked keys cannot be un-revoked. Issue a new key instead.

## How requests get logged

Each authenticated request emits a structured line in the datris container log:

```
capability check: route=POST /api/v1/pipeline required=pipeline:create key=claude-desktop legacy=false outcome=grant
```

The fields:

- `route` — HTTP method + path
- `required` — the capability the route needs (see [the capability model](#the-capability-model))
- `key` — the label of the API key (or `session:<username>` for cookie-authed UI flows)
- `legacy=true` — the key has full access via the backward-compatibility backstop; `false` means a scoped key
- `outcome` — `grant`, `would-deny`, `deny`, `unmapped`, or `rejected-key` (the presented key was revoked, unknown, or could not be verified — the request is refused before any capability is considered)

Enforcement is **on by default**: a scoped key calling a route it lacks the capability for gets `outcome=deny` and an HTTP 403. To trial a new scope policy without rejecting traffic — for example, you've issued a new scoped key and want to see what it would have been denied under real workload before pointing a production agent at it — set `CAPABILITY_ENFORCEMENT=log-only` in `.env`. Calls refused only because the key lacks a capability then succeed and emit `outcome=would-deny` log lines instead of 403s. Log-only never opens what is refused for another reason: the install-wide routes for a key or user limited to a catalog or to what it created (see [below](#keys-limited-to-a-catalog-or-to-what-they-created)), table listings for restricted users, and the scope checks made on each item. Restoring a version of a deleted tap or pipeline is one of those item checks: a key without `tap:create` for the re-created tap, or `pipeline:create` for the re-created pipeline, is refused (`403`) under log-only too, although the same key's `POST /api/v1/tap` or `POST /api/v1/pipeline` passes there as `would-deny`. Flip back to `enforce` (or remove the line) once you've validated the policy.

Every access check (capabilities, the agent policy, user roles and audit logging) reads the route of a request exactly as the server matches it to a handler, and a `HEAD` request is checked as the `GET` it runs. A route the capability table does not classify is refused (`403`, naming `*:*`) to any key or user except full-access keys and admins; under `CAPABILITY_ENFORCEMENT=log-only` it is logged as `would-deny` and allowed, and a request with no key or session is left to the route's own key check, as on every route. The platform's own routes are all classified.

## The capability model

Every API key carries a list of capability strings:

```
pipeline:read:catalog=support
document:upload:collection=support_docs
search:vector:collection=support_docs
job:read
```

Each capability is `resource:action[:scope]`. Scope segments restrict by container (catalog, collection), type, or ownership — never by leaf resource name, since agents pick those at runtime.

A scope is accepted only on a capability where the platform applies it:

| Capability | Scopes applied |
|---|---|
| `pipeline:*`, `tap:*` (every action) | `catalog=<name>`, `owner=self` (or `owner=<key label>`) |
| `secret:read`, `secret:write` | `_type=<type>` (e.g. `_type=tap`) |
| `search:vector` | `collection=<name>`: searches only that collection |
| `document:upload` | `collection=<name>`: uploads only into a pipeline whose vector destinations are all named by the key's `collection=` scopes |
| `approval:read` | `owner=self` |
| `protect:reveal` | `catalog=<name>`, `owner=self` (or `owner=<key label>`): reveals only in a pipeline in that catalog or created by that key, and only one the key may also read in that scope (for example `protect:reveal:catalog=Sales` with `pipeline:read:catalog=Sales`). Only on `protect:reveal` written out: a scoped wildcard (`*:*:catalog=Sales`, `protect:*:catalog=Sales`) grants no reveal |
| everything else (`query:*`, `job:*`, `metadata`, `config`, `mcp`, `audit`, `policy`, `incident`, `protect:admin`, `code-repo`, `approval:decide`) | none: grant it unscoped or leave it out |

For pgvector, `collection=<table>` means the table in the `public` schema and `collection=<schema>.<table>` a table in any other schema. A pgvector table whose name contains a dot, or a table in a schema whose name contains a dot, cannot be named by a `collection=` scope (the dotted form would be ambiguous), so only an unscoped capability reaches it; the same holds for a vector destination with no name. Collection names are matched exactly as written: no trimming and no case folding (a Weaviate class `Docs` needs `collection=Docs`). A scoped wildcard is accepted only when every action it covers applies the scope: `pipeline:*:catalog=Sales` is valid, `*:*:catalog=Sales` is not. `pipeline:run` scopes are accepted, but no route requires `pipeline:run` from an API key today.

Issuing a key with any other scope, an unknown resource or action, or the same scope key twice (`catalog=A,catalog=B`) is refused with `400` and a message naming the capability, the scope, and the scopes that apply, for example:

```
Invalid capability 'job:read:owner=self': scope 'owner' is not applied on job:read. Supported scopes for job:read: none. Grant 'job:read' unscoped or leave it out.
```

### Keys limited to a catalog or to what they created

A key is *limited* when it carries `catalog=` or `owner=` on at least one `pipeline:*` or `tap:*` capability and holds no unscoped `pipeline:read` (it is then limited for pipelines) or no unscoped `tap:read` (limited for taps). `pipeline:read:catalog=Sales` alone is limited for both; `pipeline:read` with `tap:run:owner=self` is limited for taps only. Keys with no `catalog=` or `owner=` on a pipeline or tap capability are not limited and see the installation as their capabilities allow: legacy and `*:*` keys, a `job:read` monitoring key, the `read-only`, `reporting`, `ops`, `full-access` and `rag-builder` templates, the platform's `recovery-agent` key and tap-run tokens.

A limited key is held to its scope on every route, as a [user limited to catalogs](/user-auth#catalog-access) is:

- **Lists and records.** Pipelines, taps, run status and history, run results, tap logs, lineage, provenance, activity signals, data discovery (`find_data`) and incidents show only the pipelines and taps the key may read. A run token of a pipeline outside the scope reads as a token with no runs: run status answers an empty list (or, with `withrollup=true`, an empty rollup that is not done), as it does for a [restricted user](/user-auth#catalog-access); a publisher token whose runs span pipelines inside and outside the scope shows only the runs inside it, with the rollup computed from them. A run result, a kill or an incident of an item outside the scope answers as an unknown one does (`404`). Pages and limits count only what the key may read: a run-status summary page holds 20 of its own rows, newest first, so every page is full until the last; the incident list and the all-taps run history read up to five times the requested limit (at most 200 incidents, 5000 runs) to fill it, so either list can still come back short when most recent activity is outside the scope. In an incident it sees, names of taps and pipelines it may not read read `[hidden]` in the step summaries and details, the trigger's error and AI summary, the outcome and the proposal. Lineage freshness of a pipeline whose feeding tap is outside the scope comes from the pipeline's own landings only (`fresh` or `unknown`, never `stale`, no cursor time). A pipeline or tap named outside the scope is `403`. A tap outside the scope that feeds one of its pipelines reads `[hidden]`, and the rows of such a run leave out the tap provenance fields (`_datris_tap_run`, `_datris_script_sha`, `_datris_source`); object-store and warehouse previews leave them out whenever the key is limited for taps.
- **Previews and search.** An object-store or warehouse preview of a pipeline outside the scope is `403`. A key limited for pipelines gets `404` for a vector collection, class or table that no pipeline in its scope writes, and search results leave out chunks other pipelines wrote.
- **Install-wide reads.** Table, collection and database listings, Unity Catalog browsing, and free-form PostgreSQL, MongoDB and natural-language queries cannot be narrowed to a catalog, so they are refused with `403` even when the key was granted `metadata:read` or the matching `query:*` capability. Custom SQL on a Snowflake, SQL Server or Databricks query (the `sql` field) is refused too, even for a pipeline in scope; leave `sql` out to preview the pipeline's table. `find_data` adds no Unity Catalog tables. The MCP activity monitor and clearing all ingestion history are refused as well. The matching MCP tools leave the key's tool list (see [MCP Server](/mcp-server#tools-for-a-key-limited-to-a-catalog-or-to-what-it-created)).
- **Writes.** Saves, runs, uploads, deletes and restores need the scope on the item as it is stored and as it would be saved (see the upgrade note below).
- **Catalog rename and detach.** Renaming a catalog, or deleting it with its items kept (detach, which moves them to Uncataloged), moves every tap and pipeline in it, so the key needs the scope on each item where it is now and `tap:create` or `tap:update` (`pipeline:create` or `pipeline:update` for pipelines) in scope where it lands: under the new name, or in Uncataloged for a detach (where the matching `delete` in scope counts too, so a key limited to what it created detaches its own items). A key limited to one catalog therefore cannot rename that catalog, or detach it while it holds items (a catalog that holds no items, only its placeholder, lands nothing in Uncataloged and detaches as before); a key whose scope covers both names (for example `catalog=Sales` and `catalog=Sales2` on create, update and read) can rename between them. The move is all or nothing: if any item is refused, the request answers `403` and nothing changes (no item, placeholder or user grant moves). The `403` names the first refused item only when the key may read it. Deleting a catalog with its items and data (cascade) keeps its per-item result: items the key may delete are deleted, the others are listed under `failed`.
- **Cancelling an enable in order.** Cancelling a catalog's ordered enable (`DELETE /api/v1/catalog/{name}/enable-ordered`) needs `tap:run` on the catalog's taps, and a key limited to a catalog or to what it created also needs `tap:read` on them in its scope. Such a key without that read gets the same `403` to a cancel whether or not an enable is running. A key that is not limited and holds no tap read gets the same answers as before. Reading the enable's status (`GET`) answers as before.

These refusals hold under `CAPABILITY_ENFORCEMENT=log-only` too, where the install-wide reads are refused to a limited key whether or not it holds their capability (in enforce mode a key that does not hold it gets the usual missing-capability `403`). A refusal for an install-wide read says that the request covers the whole installation and is not available to a key limited to a catalog or to what it created; it names nothing from the request. A key meant to list tables or run free-form queries across the installation needs unscoped `pipeline:read` and `tap:read`, or no `catalog=` / `owner=` capability at all.

### Scopes the platform does not apply

A key issued by an earlier release may hold a capability with a scope the platform never applied on it (for example `job:read:owner=self` or `query:postgres:database=x`). Earlier releases let such a capability reach the whole route, as if it were unscoped. Now it grants nothing: a request that only that capability would allow is refused with `403`, `errorKind: capability_denied`, and a message naming the capability and the scope. The key's other capabilities keep working. A stored scoped wildcard such as `*:*:catalog=Sales` keeps its pipeline and tap access under that scope and grants nothing else.

You can find these keys three ways: the server logs a `DOCTOR keys.inert_scopes` warning at startup, [`datris doctor`](/doctor) reports `keys.inert_scopes` as an error naming each key and capability, and **Configuration → API-Keys** shows a banner and marks those capabilities. Keys cannot be edited: issue a replacement key with the capability unscoped (or with a supported scope), switch the client to it, and revoke the old key.

To keep the earlier behaviour while you replace keys, set `DATRIS_KEY_INERT_SCOPES=allow` in `.env` and recreate the `datris` container. Each request that then passes only through such a capability writes a `security` / `inert-scope-used` row to the [audit log](/audit-log), and doctor reports a warning instead of an error. The opt-out restores the earlier behaviour for capabilities whose scope is not applied, with three exceptions: a wildcard key carrying a scope (such as `*:*:catalog=Sales` or `*:read:owner=self`) is never treated as an administrator key, with or without the opt-out; a key whose pipeline or tap capability carries `catalog=` or `owner=` together with a scope that is not applied is treated as limited to that catalog or owner, with or without the opt-out (that capability itself grants nothing on pipelines and taps); and a key limited by `catalog=` or `owner=` (for example `*:*:catalog=Sales`, or `pipeline:read:catalog=Sales` with `query:postgres:database=x`) is refused the install-wide listings and raw queries, and sees only its own pipelines' and taps' records, with or without the opt-out, even when the only capability naming the route is one whose scope is not applied. Remove the line once the keys are replaced.

A key holding `tap:update` with no `tap:create` at all is refused the same way. Restoring over a tap that still exists needs `tap:update` only, as before | `tap:create` in the same scope as its `tap:update`, or re-create the tap with `POST /api/v1/tap` by a caller that may create it |
| A key that restores versions of deleted pipelines (scoped or not) | Restoring a version of a pipeline that no longer exists re-creates it, so it now also needs `pipeline:create` in scope on the pipeline as re-created (the version's catalog and the version's owner, which the re-created pipeline keeps), as saving a new pipeline does; without it the restore is `403` naming `pipeline:create` and nothing is written. A key holding `pipeline:update` with no `pipeline:create` at all is refused the same way, and an `owner=self` key restores only versions it created. Restoring over a pipeline that still exists needs `pipeline:update` only, as before | `pipeline:create` in the same scope as its `pipeline:update`, or re-create the pipeline with `POST /api/v1/pipeline` by a caller that may create it |
| Every caller, administrator keys included | The MongoDB query (`POST /api/v1/query/mongodb`, `query_mongodb`) and the collection listings read data collections only. The query answers `400` `This database or collection is not available for queries.` for a system database, a `system.` collection or a collection holding platform state; the listings leave those collections out, and a system database named in the collection listing gets the same `400`. The filter and the projection follow the same operator rules | Query data collections; read platform state through its own endpoints |
| A pipeline whose MongoDB destination is a system database, a `system.` collection or a collection holding platform state, and a new or changed MongoDB destination in the platform's internal database (except on an install whose `mongodb.database` is that database) | The save or restore is refused with `400` `A MongoDB destination must be a data collection, and a new destination must be in a data database. Choose another database or collection name.`; a run fails with the same message before writing; a delete with data leaves that collection and returns a warning. Pipelines whose unchanged destination is a data collection in the internal database keep working | Point the pipeline at a data collection in a data database |
| Every caller, administrator keys included | PostgreSQL and natural-language queries (`POST /api/v1/query/postgres`, `POST /api/v1/query/natural`) run in a read-only transaction under a time limit (30 seconds; 5 minutes with `limit: -1`). A query containing a refused word returns an error naming it | Read with `SELECT` or `WITH` queries, paging a large read; write data through pipelines |
| Every caller, administrator keys included | `POST /api/v1/tap/run` accepts only `mode` `run` or `test` (missing or empty means `test`). Any other value, which earlier releases ran as a test, is now refused with `400` naming the valid values | Send `"mode": "test"` or `"mode": "run"` |
</Note>

A scoped key cannot overwrite or restore a pipeline outside its scope: saving (`POST /api/v1/pipeline`) under the name of an existing pipeline needs `pipeline:create` or `pipeline:update` in scope for that pipeline's catalog and owner, and restoring one of its versions needs `pipeline:update` in scope (for a deleted pipeline, the restored version's catalog and owner, plus `pipeline:create` there, since the restore re-creates it); otherwise the request is refused with `403` before anything is checked or written.

When a key is refused for an item outside its scope, the `403` message names the key, the capability it lacks, and the key's own capabilities for that kind of item. It never names the item's catalog or owner (or a secret's type). Admins find those in the [audit log](/audit-log#what-is-recorded), which records each refusal with the item's catalog and owner.

Tap secrets (`_type=tap`) are the only secrets a tap can read: a tap that names a platform secret is refused on save and at run time, so a key holding `tap:create` and `tap:run` cannot use a tap to read a platform secret that its `secret:read:_type=tap` scope keeps it from reading directly (unless an operator sets `DATRIS_TAP_SECRET_SCOPE=any`; see [Taps](/taps#taps-can-only-use-tap-secrets)).

`protect:reveal` (read back the original of an [`encrypt`-protected field](/transformation/field-protection#revealing-a-value)) and `protect:admin` (rotate its key, and edits to the field-protection secret) are never in a scoped template or in the editor and viewer role bundles: grant them explicitly to the key that needs them. Admins, the `full-access` template, and legacy unscoped keys hold them through `*:*`. `protect:reveal` may carry `catalog=` or `owner=self` to reveal only in pipelines in that scope, and then works only on pipelines the key may also read in that scope: grant `protect:reveal:catalog=Sales` together with `pipeline:read:catalog=Sales`. `protect:admin` takes no scope. A key limited by `catalog=` or `owner=` on a pipeline or tap capability reveals only in pipelines it may read in that scope, whatever its reveal capability says; one that holds no pipeline read in scope (for example `protect:reveal` with `tap:read:catalog=Sales`, or with `pipeline:create:catalog=Sales` alone) reveals nothing. A key holding an unscoped `protect:reveal` and no scoped pipeline or tap capability is not limited by pipeline read: it reveals in every pipeline.

Before granting a scoped reveal: `catalog=*` or `owner=*` matches every pipeline that has a catalog or a recorded creator, so it reveals almost everywhere. `owner=<another key's label>` reveals in every pipeline that key created (as it does on pipeline capabilities), and a key issued later under the same label inherits that.

Pipeline names are the binding for revealed values: a pipeline that is deleted frees its name, and a key that can create a pipeline of that name, or rename a pipeline in its scope to it (renaming needs `pipeline:delete`), with a field of the same name could reveal values the earlier pipeline wrote, if it holds them. Grant `pipeline:create` or `pipeline:delete` together with `protect:reveal` only to keys you trust with the earlier pipeline's data.

Changing the AI script a pipeline runs (its AI data-quality rule or AI transformation script) without changing the pipeline's definition is a pipeline update: regenerating it, adopting the code-repository version with pull, and restoring an earlier script version all need `pipeline:update`; listing, reading and diffing script versions need `pipeline:read`. The `rag-builder` template holds `pipeline:create` but not `pipeline:update`, so its keys cannot regenerate, pull or restore scripts; add `pipeline:update` to a key that should.

| Route | Capability |
|---|---|
| `POST /api/v1/pipelines/{name}/codegen-scripts/{kind}/regenerate` | `pipeline:update` |
| `POST /api/v1/pipelines/{name}/codegen-scripts/{kind}/pull` | `pipeline:update` |
| `POST /api/v1/pipelines/{name}/codegen-scripts/{kind}/versions/{version}/restore` | `pipeline:update` |
| `GET /api/v1/pipelines/{name}/codegen-scripts/{kind}/versions` (and one version, diff) | `pipeline:read` |

The platform's own `recovery-agent` key holds `pipeline:update` so a [pipeline incident](/incidents) can regenerate the pipeline's stored AI script; it has no `pipeline:create` or `pipeline:delete`, so it never changes a pipeline's definition. A key issued by an earlier release gains `pipeline:update` the next time the server starts (recorded in the audit log as a grant); a revoked recovery key is never changed.

When user-auth is on, logged-in browser sessions are first-class identities too: `session:admin`, `session:editor1`, etc. The capability bundle is derived from the user's role (admin → full access, editor → create/update/run, viewer → read-only). The API-Keys tab in Configuration shows scoped *keys*; per-role capabilities are managed via the **Users** tab. For a user an admin has limited to specific catalogs ([Catalog access](/user-auth#catalog-access)), the session bundle is the role bundle narrowed to `catalog=` scopes for the granted catalogs. A session request for something outside those catalogs answers `404`, as if it did not exist; an API key request outside the key's scopes answers `403`.

## Multi-tenant

`MULTI_TENANT=true` switches the model: a single `api-key-mappings` secret maps `keyValue → tenantEnv`, and every tenant carries its own per-environment data. The UI key flow above is single-tenant only; in multi-tenant mode the mappings are managed directly in the `api-key-mappings` Vault secret.

## Capabilities vs. the agent policy

A capability says what a key *may* do. The [agent policy](/agent-policy) says what an agent may do *unattended*: for each action, whether it runs on its own, waits for a person to approve it, or is refused. The policy runs after the capability check and can only pause or refuse what the key already holds — it never grants anything. Two capabilities support it: `policy:read` (read the policy; any key) and `approval:read` (list and poll the approvals the key queued; use `approval:read:owner=self`). Deciding approvals is a person's job — an agent-initiated request is refused even with `approval:decide`. An approved action runs with the requesting key's own current access: approval never lets a key do what its capabilities do not allow, and an approval whose key was revoked in the meantime does not run.
