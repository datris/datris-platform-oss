The data platform integrates with AI providers for these features:

- **Schema generation** — upload a file to `POST /api/v1/pipeline/generate` and receive a complete pipeline configuration with inferred field names and types
- **Data quality rules** — describe validation logic in plain English using `aiRule` instead of writing code
- **Transformations** — describe data transformations in plain English using `aiTransformation`
- **Data profiling** — upload a file and get summary statistics, quality issues, and suggested validation rules
- **Header validation** — AI-powered fuzzy matching for CSV/delimited file headers against the pipeline schema
- **Error explanation** — AI analyzes job failures and explains the root cause in plain English

All features use the same provider configuration.

## Choosing a Provider

The data platform supports cloud providers (Anthropic, OpenAI) and local models via Ollama.

**Cloud providers are recommended for production use.** They offer higher accuracy and stronger domain knowledge. The AI generates scripts from a sample of the data (not the full file), so there are no file size limitations tied to the model's context window.

| Provider | Accuracy | API Key | Best For |
|----------|----------|---------|----------|
| Anthropic (Claude) | Excellent | Required | Production |
| OpenAI (GPT) | Excellent | Required | Production |
| Ollama (local) | Good (varies by model) | No | Development, testing, no external dependencies |

Ollama is a good choice for local development and testing — it requires no API key, no external account, and runs entirely on your machine. For production workloads requiring strong domain knowledge in generated scripts, use a cloud provider.

## Supported Providers

| Provider | Value | API Key Required |
|----------|-------|-----------------|
| Anthropic (Claude) | `anthropic` | Yes |
| OpenAI (GPT) | `openai` | Yes |
| Ollama (local) | `ollama` | No |

## application.yaml

Enable AI and set the provider in `application.yaml`:

```yaml
ai:
  enabled: "true"
  provider: "anthropic"   # anthropic, openai, or ollama
  aiSecretName: "oss/anthropic"
```

Change `aiSecretName` to match the Vault secret name for your chosen provider.

## Vault Secret

The endpoint and model are stored in Vault. The secret must contain three fields:

| Field | Description |
|-------|-------------|
| `endpoint` | API endpoint URL |
| `model` | Model identifier |
| `apiKey` | API key (empty string `""` for Ollama) |

### Anthropic (recommended)

```bash
docker-compose exec -e VAULT_ADDR=http://vault:8200 -e VAULT_TOKEN=root-token vault \
  vault kv put secret/oss/anthropic \
  endpoint="https://api.anthropic.com/v1/messages" \
  model="claude-sonnet-4-6" \
  apiKey="your-anthropic-key"
```

Then update `application.yaml`:

```yaml
ai:
  enabled: "true"
  provider: "anthropic"
  aiSecretName: "oss/anthropic"
```

### OpenAI

```bash
docker-compose exec -e VAULT_ADDR=http://vault:8200 -e VAULT_TOKEN=root-token vault \
  vault kv put secret/oss/openai \
  endpoint="https://api.openai.com/v1/chat/completions" \
  model="gpt-4o" \
  apiKey="your-openai-key"
```

Then update `application.yaml`:

```yaml
ai:
  enabled: "true"
  provider: "openai"
  aiSecretName: "oss/openai"
```

### Ollama (local model)

[Ollama](https://ollama.com) runs models locally on the host machine and exposes an OpenAI-compatible API. No API key is required.

**Install Ollama** on your machine from [ollama.com/download](https://ollama.com/download), then pull a model:

```bash
ollama pull qwen2.5:14b-instruct
```

The data platform running in Docker reaches Ollama on the host via `host.docker.internal`. The Vault secret is seeded automatically by `docker/vault-init.sh`. To set it manually:

```bash
docker-compose exec -e VAULT_ADDR=http://vault:8200 -e VAULT_TOKEN=root-token vault \
  vault kv put secret/oss/ollama \
  endpoint="http://host.docker.internal:11434/v1/chat/completions" \
  model="qwen2.5:14b-instruct" \
  apiKey=""
```

The default model is `qwen2.5:14b-instruct`. To use a different model, set `OLLAMA_MODEL` in your `.env` file and pull it locally:

```bash
OLLAMA_MODEL=llama3.1:8b
ollama pull llama3.1:8b
```

Then `docker-compose up --build` to update the Vault secret.

#### Recommended local models

Choose a model based on your available RAM. Larger models are significantly more accurate — 70B+ models approach cloud-level quality for data validation and transformation tasks.

| Model | Size | RAM Needed | Accuracy | Best For |
|-------|------|------------|----------|----------|
| `llama3.1:8b` | 8B | ~6 GB | Good | Lightweight dev/testing |
| `qwen2.5:14b-instruct` | 14B | ~10 GB | Good | Default for 16-24 GB machines |
| `qwen2.5:32b-instruct` | 32B | ~20 GB | Very good | 32 GB machines |
| `llama3.3:70b` | 70B | ~42 GB | Excellent | 64+ GB machines, near cloud quality |
| `qwen2.5:72b-instruct` | 72B | ~45 GB | Excellent | 64+ GB machines, near cloud quality |

#### Local model accuracy

Local models work well for straightforward rules but may produce less accurate results for complex validation logic. For production workloads where accuracy matters, use a cloud provider or a 70B+ local model. For development and testing, 14B models provide fast iteration at acceptable accuracy.

## Automating with .env

To avoid setting Vault secrets manually after every `docker-compose up --build`, create a `.env` file at the project root (this file is gitignored):

```bash
OLLAMA_MODEL=qwen2.5:14b-instruct
ANTHROPIC_API_KEY=your-key-here
OPENAI_API_KEY=your-key-here
```

Docker Compose reads `.env` automatically and passes these values to `vault-init`, which seeds the secrets on every startup.

## Verifying the Secret

```bash
docker-compose exec -e VAULT_ADDR=http://vault:8200 -e VAULT_TOKEN=root-token vault \
  vault kv get secret/oss/anthropic
```

## AI Provider Required

An AI provider must be configured for the platform to start. Set `ai.enabled: "true"` and configure at least one provider (Anthropic, OpenAI, or Ollama) in `application.yaml` and Vault.

## Multi-Tenant: Per-Tenant API Key Overrides

In multi-tenant deployments (`multiTenant: "true"` in `application.yaml`) each tenant can override the global AI provider key with their own. The platform resolves the AI config per-request: if a Vault secret exists at `{tenantEnv}/{provider}` (for example `trial-alice/anthropic` or `trial-alice/openai`) it is used as an override; otherwise the global `ai.aiSecretName` from `application.yaml` is used as a fallback. No restart, no code changes — the override takes effect on the next AI call.

### Why bring your own key

The global key configured by the operator is often a shared, rate-limited, cost-conscious default — fine for evaluating the platform but a bottleneck for serious work. Bringing your own key lets you:

- Run AI features against your own quota and account, with no shared rate limits
- Pick a stronger model than the operator-configured default
- Isolate cost and usage tracking to your own provider account
- Get dramatically faster, higher-quality results from CodeGen, AI lookups, data quality rules, transformations, and schema inference

This is especially relevant for the hosted free trial at [datris.ai](https://datris.ai), where the shared Datris-managed key is conservatively budgeted.

### Setting your key from the UI (Configuration tab)

The easiest way for an end user to override their tenant key is through the platform UI:

1. Open the **Configuration** tab.
2. Pick a provider (`Anthropic` or `OpenAI`), select a model, and paste your API key.
3. Click **Save Configuration**.

The status indicator at the top of the page flips from "Datris-managed keys (default)" to "Your own {provider} key". From this point on, all AI features run against your key.

To revert to the operator-configured shared key, click **Reset to Datris-managed**. This deletes the per-tenant Vault secrets and falls the tenant back to the global default.

### Setting a tenant key directly in Vault

For operators who provision tenants programmatically, write the secret directly to the tenant's Vault path:

```bash
docker-compose exec -e VAULT_ADDR=http://vault:8200 -e VAULT_TOKEN=root-token vault \
  vault kv put secret/trial-alice/anthropic \
  endpoint="https://api.anthropic.com/v1/messages" \
  model="claude-sonnet-4-6" \
  apiKey="sk-ant-..."
```

Replace `trial-alice` with the tenant's environment name. The secret shape (`endpoint`, `model`, `apiKey`) is the same as the global secret described under [Vault Secret](#vault-secret) above.

### Resolution chain

The fallback chain for the main AI provider config in multi-tenant mode is:

1. Tenant's `{env}/anthropic` (or `{env}/openai`) Vault secret, if it exists
2. Global `ai.aiSecretName` from `application.yaml`

The codegen secret follows an independent fallback chain — see [Multi-tenant](#multi-tenant) under "Stronger Model for Code Generation" below. A tenant can override the main key, the codegen key, or both, in any combination.

## Stronger Model for Code Generation

Some AI tasks generate executable code: tap script generation, AI data quality rules (`aiRule`), AI transformations (`aiTransformation`), JSON Schema / XSD generation, and natural-language → SQL. The quality of these outputs is directly tied to the model's coding ability.

By default the platform points code-generation tasks at a stronger model than the one used for general AI calls (error explanation, brainstorm chat, CRON generation, profiling, etc.). Cheap chatty paths stay on the default model so you only pay the upgrade on the calls that benefit.

### Defaults

The `oss/codegen` Vault secret is seeded automatically by `docker/vault-init.sh` based on `AI_PROVIDER`, reusing the same API key as your main provider:

| `AI_PROVIDER` | Main model | Codegen model | API key |
|---|---|---|---|
| `anthropic` | `claude-sonnet-4-6` | `claude-opus-4-6` | `ANTHROPIC_API_KEY` |
| `openai` | `gpt-4o` | `gpt-5.4` | `OPENAI_API_KEY` |
| `ollama` | `${OLLAMA_MODEL}` | `${OLLAMA_MODEL}` (same — keeps RAM footprint flat) | none |

Override the codegen model by setting `CODEGEN_MODEL` in `.env`:

```bash
CODEGEN_MODEL=claude-opus-4-6
```

### application.yaml

The default config enables codegen with the seeded secret:

```yaml
ai:
  enabled: "true"
  provider: "anthropic"
  aiSecretName: "oss/anthropic"
  version: "2023-06-01"
  codegen:
    secretName: "oss/codegen"
```

### Disabling

To use the same model for codegen as for everything else, remove the `codegen:` block from `application.yaml` and restart. The platform falls back to the main `ai.*` config with zero behavior change.

### Which call sites switch

| Feature | Uses codegen config? |
|---|---|
| Tap script generation (`fetch()` Python) | Yes |
| Tap script auto-fix | Yes |
| AI data quality rules (`aiRule`) | Yes |
| AI transformations (`aiTransformation`) | Yes |
| CSV / JSON Schema / XSD generation | Yes |
| Natural language → SQL (`/query/ai`) | Yes |
| CRON generation, brainstorm chat, error explanation | No (cheap, stays on default) |
| Data profiling, AI question answering | No (analysis/prose, stays on default) |
| AI header validation | No (classification, stays on default) |

### Multi-tenant

In multi-tenant deployments each tenant can override the codegen model independently by creating a Vault secret at `{tenantName}/codegen` with the same `{endpoint, model, apiKey}` shape. The fallback chain is:

1. Tenant's `{env}/codegen` Vault secret (if it exists)
2. Global codegen config (if `ai.codegen.secretName` is set)
3. Tenant's main AI config
4. Global main AI config

The same per-tenant override pattern applies to the **main** AI provider key independently — see [Multi-Tenant: Per-Tenant API Key Overrides](#multi-tenant-per-tenant-api-key-overrides) above. A tenant can override the main key, the codegen key, or both.

### Misconfiguration

If `ai.codegen.secretName` points to a missing or malformed secret at startup, the platform fails to start with a clear error — there's no silent fallback to the main config.
