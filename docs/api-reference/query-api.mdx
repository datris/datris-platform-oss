The Query API provides REST endpoints for querying every structured destination — PostgreSQL, MongoDB, object store, Snowflake, Databricks, and SQL Server — plus natural language queries and AI-powered answers. These endpoints mirror the MCP tools, making the same retrieval capabilities available via HTTP.

In the web UI, the Search tab's Traditional mode can also query Databricks, Snowflake and SQL Server pipelines (under **Warehouse**): pick the pipeline and run read-only SQL against its destination table through the pipeline's own warehouse or server and credentials.

The two AI endpoints are documented with the Search API, next to the vector search they are usually paired with: [`POST /api/v1/query/natural`](/api-reference/search-api#natural-language-query) turns a plain-English question into SQL and runs it against PostgreSQL, and [`POST /api/v1/ai/answer`](/api-reference/search-api#ai-answer-rag) generates an answer from context you pass in (typically retrieved chunks). This page covers the direct, read-only SQL and document queries against each destination.

## Query PostgreSQL

Execute a read-only SQL SELECT query against PostgreSQL.

```
POST /api/v1/query/postgres
```

### Request

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `sql` | string | Yes | | SQL SELECT query to execute |
| `database` | string | No | `datris` | PostgreSQL database name to connect to |
| `limit` | integer | No | 100 | Maximum rows to return. Pass `-1` for unlimited (tap scripts use this to read every row). Omit for the preview default of 100; any positive value is honored with no cap. |

### Example

```bash
curl -X POST http://localhost:8080/api/v1/query/postgres \
  -H "Content-Type: application/json" \
  -d '{
    "sql": "SELECT symbol, date, close FROM test.stock_price WHERE volume > 1000000",
    "database": "datris",
    "limit": 10
  }'
```

### Response

```json
{
  "results": [
    {
      "symbol": "AAPL",
      "date": "2024-01-15",
      "close": 185.92
    }
  ],
  "count": 1
}
```

### Safety

The endpoint enforces multiple layers of protection:

- **Read-only transaction** — every query runs inside a transaction that PostgreSQL itself treats as read-only and that is never committed, so a query cannot change data. Each query starts from a clean session.
- **Time limit** — a query is cancelled after 30 seconds, or after 5 minutes when `limit` is `-1`; a cancelled query returns an error and no rows. Page a large read.
- **SELECT-only** — only queries starting with `SELECT` (or `WITH`) are allowed
- **Statement blocklist** — queries containing `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `TRUNCATE`, `GRANT`, `REVOKE`, `COPY`, `CALL`, `EXECUTE`, or `EXEC` are rejected, as are queries that call server administration, server file, replication or remote-connection functions, or a small set of other functions; the error names the word. Words are matched anywhere in the query, string literals included. One quoting form, Unicode-escape quoting (`U&`), is not accepted.
- **No stacked queries** — semicolons are not allowed
- **No SQL comments** — `--` and `/* */` are rejected to prevent obfuscation
- **LIMIT enforcement** — if no `LIMIT` is present in the SQL, one is appended automatically using the request's `limit` value (or the default 100). Pass `limit: -1` to bypass the automatic append entirely — the caller's SQL runs as-is.

A query refused by one of these checks (an empty query, a query that does not start with `SELECT` or `WITH`, a blocked word or function, a semicolon, a comment, `U&` quoting) returns `500 Internal Server Error` with `{"error": "..."}`, the message naming the rule (for example `Only SELECT queries are allowed (WITH/CTE is also permitted)` or `Query contains blocked keyword: DROP`).

Queries run with the platform's own PostgreSQL credentials (the PostgreSQL secret), which pipelines also use to load data. As for any service account, give that secret a role with only the privileges it needs (create and write in the destination schemas) rather than a superuser.

## Query MongoDB

Query a MongoDB collection with optional filter and projection.

```
POST /api/v1/query/mongodb
```

### Request

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `collection` | string | Yes | | MongoDB collection name |
| `database` | string | No | configured MongoDB database | MongoDB database name to query. |
| `filter` | object | No | `{}` | MongoDB query filter |
| `projection` | object | No | all fields | Fields to include/exclude |
| `limit` | integer | No | 20 | Maximum documents to return. Pass `-1` for unlimited (tap scripts use this to read every document). Omit for the preview default of 20; any positive value is honored with no cap. |

### Example

```bash
curl -X POST http://localhost:8080/api/v1/query/mongodb \
  -H "Content-Type: application/json" \
  -d '{
    "collection": "orders",
    "filter": {"status": "active"},
    "projection": {"name": 1, "_id": 0},
    "limit": 10
  }'
```

### Response

```json
{
  "results": [
    {
      "name": "Order-001"
    }
  ],
  "count": 1
}
```

### Safety

- **Data collections only** — queries read data collections only: never MongoDB's own system databases, `system.` collections, or the collections in which the platform keeps its own state. Any of these returns `400` with `{"error": "This database or collection is not available for queries."}`.
- **Blocked operators** — a filter or a projection containing `$where`, `$function`, or `$accumulator`, at any depth (nested documents and arrays included), is rejected, as these allow arbitrary JavaScript execution
- **Projection** — plain inclusion and exclusion (`1`, `0`, `true`, `false`), `$slice`, `$elemMatch`, `$meta` and aggregation expressions other than the blocked operators are accepted
- **Limit** — `limit` is applied as given; `-1` returns every matching document (tap scripts use this), so pass a positive `limit` for previews
- **Standard MongoDB query operators** (`$eq`, `$gt`, `$in`, `$regex`, etc.) are safe and fully supported

A filter or projection holding a blocked operator returns `500 Internal Server Error` with `{"error": "..."}` naming it, for example `MongoDB filter contains blocked operator: $where`; an empty collection name returns `500` too. A system or platform collection returns `400`, as above.

## Query Object Store

Read rows from a pipeline's object store destination (MinIO or S3). The pipeline name selects the bucket, prefix, and credentials — the caller never supplies connection details.

For a restricted user: the response omits `_datris_tap_run`, `_datris_script_sha`, `_datris_source`. When the pipeline's saved `prefixKey` or `destinationBucketOverride` is not a plain path (a wildcard or escape character `* ? [ ] { } \`, leading or trailing spaces, or an empty, `.` or `..` segment), the query is refused with `400` and `The object-store prefix and bucket must be plain names: no wildcard or escape characters (* ? [ ] { } \), no leading or trailing spaces and no empty, '.' or '..' path segments. Choose a plain prefix.`; change the prefix to preview it.

```
POST /api/v1/query/objectstore
```

### Request

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `pipeline` | string | Yes | | Pipeline name. Must be a pipeline with an object store destination. |
| `limit` | integer | No | 100 | Maximum rows to return. Values of 0 or less fall back to 100; capped at 10,000. |

### Example

```bash
curl -X POST http://localhost:8080/api/v1/query/objectstore \
  -H "Content-Type: application/json" \
  -d '{
    "pipeline": "sales_data",
    "limit": 10
  }'
```

### Response

```json
{
  "pipeline": "sales_data",
  "path": "s3a://datris-bucket/sales_data",
  "format": "parquet",
  "columns": ["symbol", "date", "close"],
  "results": [
    {
      "symbol": "AAPL",
      "date": "2024-01-15",
      "close": 185.92
    }
  ],
  "count": 1,
  "snapshotId": null,
  "snapshotTimestamp": null
}
```

`snapshotId` and `snapshotTimestamp` identify the Iceberg snapshot that was read; both are `null` for Parquet and ORC pipelines.

`columns` lists the pipeline's destination schema in its order, then the provenance stamp columns, then any other columns the files hold (for example one whose field was removed from the schema), then partition columns the schema does not name. A column added by a later file is `null` for rows written before it existed, and a schema column no file holds yet is `null` in every row. A column the files hold keeps the files' letter case. Values come back under the types the files hold them in, so changing a field's type does not change what earlier files return.

How the files are read depends on the location:

- **Up to 1,000 data files** (the usual case): the query reads every file's schema first (remembering it for later queries until the file changes), so the result has every column the files hold and only the stamp columns they hold. When files hold one column under different types, the column still comes back as numbers if every type fits one number type exactly (`tinyint`, `smallint`, `int` and `bigint`; `float` and `double`; `int` or `float` with `double`; decimals, at the widest scale, up to 38 digits). Any other mix, such as `int` with `string` or `date` with `timestamp`, comes back as text in every row (dates as `2024-01-02`, timestamps as ISO instants, booleans as `true`/`false`). This is decided from every file, so it does not depend on `limit`.
- **More than 1,000 data files, or when reading the schemas cannot finish** (a file that is not a readable data file, a file removed during the query, or more than about 10 seconds spent): the query reads the way it always has, from one sampled file's columns and types, plus the schema's columns and the stamp columns the pipeline stamps now (listed even when no file holds them, as `null`). Columns the sampled file lacks are read under the schema's type (a `tinyint` or `smallint` as `int`) and take the schema's letter case; if that read fails, the query returns only the sampled file's columns, and on Parquet, if the files hold one of those under two types, it fails with an error saying so. A value read under a type it does not match can come back wrong with no error: on ORC as `null` or as a converted value (for example 1.5 as 1), on Parquet when a whole number and a date are read as each other (a date as its day count, a number as a date). A file Spark cannot read fails the query only if the read reaches it before `limit` rows are found. Because the schema reading can finish on one call and not on the next (for example on a slow store before its schemas are remembered), the same query can switch between the two ways and return a different set of columns or types from one call to the next.

Empty files are skipped. An Iceberg pipeline returns the table's current columns.

If the pipeline exists but no runs have written data yet, or its location holds no data files, the endpoint returns an empty result (`"count": 0`) rather than an error.

### Error Cases

Returns `400 Bad Request` with `{"error": "..."}` when:

- The pipeline is not found
- The pipeline does not have an object store destination
- The pipeline's object store configuration is missing a prefix key
- The read times out (default 90 seconds, tunable via the `DATRIS_OBJECTSTORE_QUERY_TIMEOUT_SEC` environment variable)

## Query Snowflake

Execute a read-only query against the Snowflake account a pipeline loads into. The pipeline name selects the credentials, warehouse, database, and schema — credentials never leave the server.

For a restricted user: `sql` is refused with `403` and the response omits `_datris_tap_run`, `_datris_script_sha`, `_datris_source`.

```
POST /api/v1/query/snowflake
```

### Request

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `pipeline` | string | Yes | | Pipeline name. Must be a pipeline with a Snowflake destination. |
| `sql` | string | No | `SELECT * FROM {destination table}` | SQL to execute. When omitted, previews the pipeline's destination table. |
| `limit` | integer | No | 100 | Maximum rows to return. Pass `-1` for unlimited; the query then runs under a 5-minute time limit instead of 30 seconds. |

### Example

```bash
curl -X POST http://localhost:8080/api/v1/query/snowflake \
  -H "Content-Type: application/json" \
  -d '{
    "pipeline": "sales_data",
    "sql": "SELECT symbol, close FROM SALES_DB.PUBLIC.STOCK_PRICE WHERE volume > 1000000",
    "limit": 10
  }'
```

### Response

```json
{
  "pipeline": "sales_data",
  "sql": "SELECT symbol, close FROM SALES_DB.PUBLIC.STOCK_PRICE WHERE volume > 1000000 LIMIT 10",
  "results": [
    {
      "SYMBOL": "AAPL",
      "CLOSE": 185.92
    }
  ],
  "count": 1
}
```

The `sql` field echoes the query that actually ran, including any automatically appended `LIMIT`.

### Safety

- **Read-only allowlist** — queries must start with `SELECT`, `WITH`, `SHOW`, `DESCRIBE`, or `DESC`. `SHOW`/`DESCRIBE` are allowed so agents can discover databases, schemas, tables, and columns.
- **Statement blocklist** — queries containing `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `TRUNCATE`, `GRANT`, `REVOKE`, `CALL`, `EXECUTE`, `EXEC`, `PUT`, `REMOVE`, `COPY`, `MERGE`, or `USE` are rejected (`USE` is blocked so a query cannot re-point the session at another database or role)
- **No stacked queries** — semicolons are not allowed
- **No SQL comments** — `--` and `/* */` are rejected to prevent obfuscation
- **LIMIT enforcement** — if a `SELECT`/`WITH` query has no `LIMIT`, one is appended using the request's `limit` value. `SHOW`/`DESCRIBE` output is row-capped at the same value.
- **Function blocklist** — a query that calls a `SYSTEM$` function is rejected with the function named (`Query contains blocked function: <name>`), except the read-only `SYSTEM$TYPEOF`, `SYSTEM$CLUSTERING_INFORMATION` and `SYSTEM$CLUSTERING_DEPTH`. This covers functions that cancel or abort other queries, sessions or transactions, resume pipes or tasks, or wait (`SYSTEM$CANCEL_QUERY`, `SYSTEM$ABORT_SESSION`, `SYSTEM$WAIT` and others). `NEXTVAL` is rejected anywhere, since reading it advances a sequence. Like the statement blocklist, the check covers string literals too.
- **Query timeout** — 30 seconds, bounding both hung requests and warehouse spend; 5 minutes when `limit: -1`. A cancelled query returns an error and no rows.

<Note>
Snowflake has no read-only session. The query runs as the pipeline's credentials role, so the blocklists are a second line and that role's grants are the real control: give the pipeline a least-privilege role. External functions cannot be told apart by name and are bounded only by those grants.
</Note>

### Error Cases

Returns `400 Bad Request` with `{"error": "..."}` when:

- The pipeline is not found
- The pipeline does not have a Snowflake destination
- The SQL fails validation (allowlist, blocklist, semicolons, comments)

|-------|------|----------|---------|-------------|
| `pipeline` | string | Yes | | Pipeline name. Must be a pipeline with a Databricks destination. |
| `sql` | string | No | `SELECT * FROM {destination table}` | SQL to execute. When omitted, previews the pipeline's destination table. |
| `limit` | integer | No | 100 | Maximum rows to return. Pass `-1` for unlimited; the query then runs under a 5-minute time limit instead of 30 seconds. |

### Example

```bash
curl -X POST http://localhost:8080/api/v1/query/databricks \
  -H "Content-Type: application/json" \
  -d '{
    "pipeline": "sales_data",
    "sql": "SELECT symbol, close FROM main.default.stock_price WHERE volume > 1000000",
    "limit": 10
  }'
```

### Response

```json
{
  "pipeline": "sales_data",
  "sql": "SELECT symbol, close FROM main.default.stock_price WHERE volume > 1000000 LIMIT 10",
  "results": [
    {
      "symbol": "AAPL",
      "close": 185.92
    }
  ],
  "count": 1
}
```

The `sql` field echoes the query that actually ran, including any automatically appended `LIMIT`.

### Safety

Same allowlist, semicolon and comment rules, `LIMIT` enforcement and time limit (30 seconds; 5 minutes when `limit: -1`) as [Query Snowflake](#query-snowflake), with the statement blocklist extended for Databricks-specific data-movement and maintenance verbs: `OPTIMIZE`, `VACUUM`, `RESTORE`, `CLONE`, `REFRESH`, `MSCK`, and `DECLARE` are also rejected.

A query that calls one of these functions is rejected with the function named (`Query contains blocked function: <name>`): `http_request`, `remote_query`, every `ai_*` function (`ai_query`, `ai_gen` and the rest), `vector_search`, `secret`, `try_secret`, `read_files`, `read_kafka`, `read_kinesis`, `read_pubsub`, `read_pulsar`, `java_method`, `reflect` and `try_reflect`. Only a call is refused (the name followed by `(`), so a column named `secret` or a table named `ai_results` still reads. The check covers string literals too.

Databricks has no read-only session. The query runs as the pipeline's credentials identity, so the blocklists are a second line and that identity's grants are the real control.

<Note>
If the SQL warehouse is stopped, opening the connection blocks while it auto-starts — this happens before the 30-second query timeout applies, so the first query after idle time can take longer.
</Note>

### Error Cases

Returns `400 Bad Request` with `{"error": "..."}` when:

- The pipeline is not found
- The pipeline does not have a Databricks destination
- The SQL fails validation (allowlist, blocklist, semicolons, comments)

## Query SQL Server

Execute a read-only T-SQL query against the SQL Server or Azure SQL database a pipeline loads into. The pipeline name selects the credentials secret, host, database, and schema — credentials never leave the server, and every `authMethod` the destination supports works here. Requires the `query:sqlserver` capability. The `read-only` and `reporting` key templates and the editor and viewer roles include it; a key issued before this capability existed keeps its explicit list, so add `query:sqlserver` to it or issue a new key.

For a restricted user: `sql` is refused with `403` and the response omits `_datris_tap_run`, `_datris_script_sha`, `_datris_source`.

```
POST /api/v1/query/sqlserver
```

### Request

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `pipeline` | string | Yes | | Pipeline name. Must be a pipeline with a SQL Server destination. |
| `sql` | string | No | `SELECT * FROM {schema}.{table}` | T-SQL to execute. When omitted, previews the pipeline's destination table. |
| `limit` | integer | No | 100 | Maximum rows to return. `0` means the default; there is no upper bound. Pass `-1` for unlimited; the query then runs under a 5-minute time limit instead of 30 seconds. |

### Example

```bash
curl -X POST http://localhost:8080/api/v1/query/sqlserver \
  -H "Content-Type: application/json" \
  -d '{
    "pipeline": "sales_data",
    "sql": "SELECT symbol, [close] FROM dbo.stock_price WHERE volume > 1000000",
    "limit": 10
  }'
```

### Response

```json
{
  "pipeline": "sales_data",
  "sql": "SELECT TOP (10) * FROM (SELECT symbol, [close] FROM dbo.stock_price WHERE volume > 1000000) q",
  "results": [
    {
      "symbol": "AAPL",
      "close": 185.92
    }
  ],
  "count": 1
}
```

The `sql` field echoes the query that actually ran, including the row cap.

### Row cap

T-SQL has no `LIMIT`, so the server caps rows one of two ways:

- **Top-level `ORDER BY`, no `TOP`** — `OFFSET 0 ROWS FETCH NEXT <limit> ROWS ONLY` is appended, keeping the order. An `ORDER BY` inside parentheses (a subquery or `OVER (...)`) does not count.
- **Anything else** (including `SELECT TOP n ... ORDER BY`, since SQL Server does not allow `TOP` and `OFFSET` together) — the statement is wrapped: `SELECT TOP (<limit>) * FROM (<sql>) q`. For a `WITH` statement the CTEs stay in front and only the final statement is wrapped.
- A statement that already has `OFFSET ... FETCH` runs as written.

When SQL Server rejects the wrapper itself (a result column without a name such as `COUNT(*)`, two columns with the same name from a join, or `FOR JSON` / `FOR XML`), the query runs unwrapped with the same row cap applied by the driver. Give computed columns an alias (`COUNT(*) AS n`) to see the wrapped form.

### Safety

- **Read-only allowlist** — queries must start with `SELECT` or `WITH`. For metadata, select from `INFORMATION_SCHEMA` views, for example `SELECT TABLE_SCHEMA, TABLE_NAME FROM INFORMATION_SCHEMA.TABLES` or `SELECT COLUMN_NAME, DATA_TYPE FROM INFORMATION_SCHEMA.COLUMNS WHERE TABLE_NAME = 'orders'`.
- **Statement blocklist** — queries containing `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `TRUNCATE`, `GRANT`, `REVOKE`, `DENY`, `EXEC`, `EXECUTE`, `MERGE`, `INTO` (so `SELECT ... INTO` cannot create a table), `USE`, `BULK`, `OPENROWSET`, `OPENDATASOURCE`, `OPENQUERY`, `DBCC`, `BACKUP`, `RESTORE`, `SHUTDOWN`, `KILL`, `RECONFIGURE`, `WAITFOR`, `DECLARE`, `TRIGGER`, `SETUSER`, `REVERT`, `WRITETEXT` or `UPDATETEXT` are rejected. The check covers the whole statement, string literals included, so `WHERE note = 'please delete'` is rejected too
- **No stacked queries** — semicolons are not allowed
- **No SQL comments** — `--` and `/* */` are rejected to prevent obfuscation
- **One statement** — T-SQL needs no semicolon between statements, so the query is scanned: a second `SELECT` that does not follow `UNION`, `UNION ALL`, `EXCEPT` or `INTERSECT` is rejected with `Only one statement is allowed in a query`, as are an unterminated string literal or quoted identifier and parentheses that do not balance. Subqueries, CTEs and `CASE ... END` are fine.
- **Control-flow and transaction words** — `SET`, `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVE`, `WHILE`, `IF`, `GOTO`, `PRINT`, `RAISERROR`, `CHECKPOINT`, `OPEN`, `CLOSE`, `DEALLOCATE`, `RETURN`, `BREAK`, `CONTINUE`, `READTEXT` and the phrase `NEXT VALUE FOR` (which advances a sequence) are rejected outside string literals and quoted identifiers, so `WHERE note = 'set if while'` and `SELECT [set] FROM t` still run. `OFFSET ... FETCH NEXT ... ROWS ONLY` is fine.
- **Rolled back** — the query runs in a transaction that is always rolled back, never committed.
- **Query timeout** — 30 seconds; 5 minutes when `limit: -1`. A cancelled query returns an error and no rows.

### Error Cases

Returns `400 Bad Request` with `{"error": "..."}` when:

- The pipeline is not found
- The pipeline does not have a SQL Server destination
- The SQL fails validation (allowlist, blocklist, semicolons, comments)
- SQL Server rejects the query (unknown table or column, ambiguous column, syntax error, permission denied, a value that will not convert)
- The connection is refused (the message names the auth method and the fix, as for loads)

Returns `502 Bad Gateway` when SQL Server fails for a reason outside the query.

## Kill Job

Kill a running pipeline job by its pipeline token. The job thread is interrupted and the job is marked as cancelled.

```
POST /api/v1/job/kill
```

### Request

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `pipelineToken` | string | Yes | Pipeline token of the running job to kill |

### Example

```bash
curl -X POST http://localhost:8080/api/v1/job/kill \
  -H "Content-Type: application/json" \
  -d '{
    "pipelineToken": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
  }'
```

### Response

```json
{
  "status": "cancelled",
  "pipelineToken": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

### Error Cases

- Job not found for the given pipeline token
- Job is not in `PROCESSING` state (already completed or cancelled)
- Job thread is no longer alive
