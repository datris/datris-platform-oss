Manage pipeline configurations through CRUD operations.

## Get a Pipeline

```
GET /api/v1/pipeline?pipeline={name}
```

**Parameters:**
| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `pipeline` | query | Yes | Pipeline name |

**Example:**
```bash
curl "http://localhost:8080/api/v1/pipeline?pipeline=sales_data"
```

**Response:** `200 OK` with the full PipelineConfig JSON.

## Unity Catalog sync state

```
GET /api/v1/pipelines/{name}/unity-catalog
```

The last Unity Catalog sync for a pipeline that sets `unityCatalog.enabled` (or that the install default `DATRIS_UNITY_CATALOG_DEFAULT=enabled` turned on): the metadata push and lineage for a Databricks pipeline (see [Databricks](/destinations/databricks#unity-catalog-metadata)), or the table registration for an object store Iceberg pipeline (see [Register Iceberg tables](/destinations/unity-catalog#register-iceberg-tables)).

**Example:**
```bash
curl http://localhost:8080/api/v1/pipelines/orders_pipeline/unity-catalog
```

**Response:** `200 OK`. `enabled` says whether Unity Catalog is on for the pipeline and `enabledBy` says who decided: `pipeline` (the pipeline's own `unityCatalog` block, including an `"enabled": false` opt-out), `default` (the install default turned on a Databricks pipeline with no block), or `null` (off, no block). `lineageEnabled` follows the same resolution. `syncSwitchedOff` is `true` while `DATRIS_UNITY_CATALOG_SYNC=false`: nothing is written to Unity Catalog even when `enabled` is `true`. `coordinates` gives the Unity Catalog table (Databricks destinations only). `state` is `never` (no sync yet), `synced`, or `error` (with `lastError` holding the warehouse's message, or when the last `catalogMode: rest` run was refused; see `restRefusedReason`). `lastSyncAt` and `lastRunId` identify the last sync. `lineage` is the lineage publish status: `off` (`unityCatalog.lineage` is `false`, or the push is off), `never`, `published`, or `error` (the failure is a `lastError` line starting with `uc-lineage:`); `lastLineageAt` is when lineage was last published and `lineageHash` identifies the published definition (see [Lineage in Unity Catalog](/destinations/unity-catalog#lineage-in-unity-catalog)). For an object store Iceberg pipeline, `coordinates` names the registered table (`catalog.schema.table`, with `kind: "iceberg"` and the table's `location`), `registerEnabled` says whether registration is on, and `register` is `off`, `never`, `registered`, `stale` (Unity Catalog still points at an older metadata file) or `error` (the failure is a `lastError` line starting with `uc-register:`); `registeredMetadataLocation` and `lastRegisterAt` record the last registration. `catalogMode` is `register`, `rest` or `managed` (see [Keep the catalog current](/destinations/unity-catalog#keep-the-catalog-current-catalogmode-rest) and [Databricks: catalogMode managed](/destinations/unity-catalog#databricks-catalogmode-managed)); in `managed` mode `register` is `managed` when the last run committed through the catalog, `restMetadataLocation` is under the location the catalog chose, and `coordinates.location` is that location once known; in `rest` mode `register` is `rest` when the last run committed through the catalog and `refused` when it wrote by path instead, `restMetadataLocation` and `lastRestCommitAt` record the last catalog commit, and `restRefusedReason` says why a run was refused. `restCreatedTable` names a table the catalog created for the pipeline at a location Datris refused (a Databricks managed table): it was never written to, and an admin has to drop it. `404` if the pipeline does not exist.

```json
{
  "pipeline": "orders_pipeline",
  "enabled": true,
  "enabledBy": "pipeline",
  "syncSwitchedOff": false,
  "coordinates": { "catalog": "datris", "schema": "default", "table": "orders", "qualified": "datris.default.orders" },
  "state": "synced",
  "lastSyncAt": "2026-09-29T12:00:00Z",
  "lastRunId": "...",
  "lineageEnabled": true,
  "lineage": "published",
  "lineageHash": "...",
  "lastLineageAt": "2026-09-29T12:00:01Z",
  "registerEnabled": false,
  "register": "off"
}
```

For an object store Iceberg pipeline:

```json
{
  "pipeline": "orders_lake",
  "enabled": true,
  "coordinates": { "catalog": "analytics", "schema": "default", "table": "orders_lake", "qualified": "analytics.default.orders_lake", "kind": "iceberg", "location": "s3a://my-lake/orders" },
  "registerEnabled": true,
  "register": "registered",
  "registeredMetadataLocation": "s3a://my-lake/orders/metadata/00001-....metadata.json",
  "lastRegisterAt": "2026-09-29T12:00:02Z"
}
```

## Create or Update a Pipeline

```
POST /api/v1/pipeline
Content-Type: application/json
```

**Body:** Full PipelineConfig JSON (see [Pipeline Configuration](/pipeline-configuration)).

**Parameters:**
| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `changeNote` | query | No | Note recorded on the saved pipeline version |

**Example:**
```bash
curl -X POST http://localhost:8080/api/v1/pipeline \
  -H "Content-Type: application/json" \
  -d '{
    "name": "sales_data",
    "source": {
      "schemaProperties": {
        "fields": [
          {"name": "id", "type": "int"},
          {"name": "amount", "type": "double"}
        ]
      },
      "fileAttributes": {
        "csvAttributes": {"delimiter": ",", "header": true, "encoding": "UTF-8"}
      }
    },
    "destination": {
      "database": {
        "dbName": "mydb",
        "schema": "public",
        "table": "sales",
        "usePostgres": true
      }
    }
  }'
```

**Response:** `200 OK`

```json
{"warnings": []}
```

`warnings` is advisory: the pipeline is saved either way. It is empty unless something about the configuration will not work as written, for example an object store Iceberg pipeline whose Unity Catalog secret points at a Databricks workspace with `catalogMode` `register` or `rest` (Databricks cannot serve either; the warning says to set `catalogMode` `managed` or use the databricks destination). Each warning is also written to the server log.

**Validation:** The configuration is validated before saving. Invalid configurations return `400` with `{"error": "<message>"}` and nothing is saved; `500` means the server itself failed. See [Pipeline Configuration](/pipeline-configuration) for all constraints.

**Database destination names:** for every caller and every pipeline type (structured, semi-structured and unstructured), a new or changed `destination.database` section must pass the same checks as on a structured pipeline: `dbName`, `table` and (except MongoDB) `schema` are required and use only `a-z`, `A-Z`, `0-9` and `_`, `options` entries must not contain `;`, and exactly one of `usePostgres`, `useMongoDB`, `useSnowflake`, `useDatabricks` or `useSqlServer` is set. With `usePostgres`, `dbName`, `schema` and `table` are also at most 63 bytes. A save that breaks one returns `400` with that check's message, for example `'destination.database.table' value 'a b' is invalid. Valid characters are a-z, A-Z, 0-9 and _`. A save that keeps exactly the `dbName`, `schema`, `table`, `warehouse`, `options` and engine flags the saved pipeline already has is not refused by this rule. The same check applies to version restore and catalog restore.

**Field types:** for every caller and every pipeline type (structured, semi-structured and unstructured), each new or changed field type in `source.schemaProperties` or `destination.schemaProperties` must be written exactly in one of these forms, in any letter case: `boolean`, `int`, `tinyint`, `smallint`, `bigint`, `float`, `double`, `string`, `date`, `timestamp`, `decimal(p)` or `decimal(p,s)` (each number 1 to 4 digits), `varchar(n)` or `char(n)` (1 to 9 digits), or `varchar(max)`; spaces are allowed inside the parentheses and after the closing `)` (not before the type name, between the name and `(`, or after a plain type name; no tabs or line breaks). On structured and semi-structured pipelines the validator also refuses `integer`, which an unstructured pipeline may carry, as before; a missing type gets the same `400`. Otherwise the save returns `400` with `Invalid field type passed: <type> for field '<name>' in the <source|destination> schema, supported types include ...` (at most 80 characters of the type are shown). A save that keeps a field with the same name and type in the same schema as the saved pipeline is not refused by this rule. The same check applies to version restore and catalog restore.

**Field names:** on structured and semi-structured pipelines, each field name in `source.schemaProperties` or `destination.schemaProperties` uses only `a-z`, `A-Z`, `0-9` and `_`; otherwise the save returns `400` with `Column name: <name> is invalid.  Valid characters are a-z, 0-9 and _`. A name the saved pipeline already has, exactly as written, in the same schema (for example a column [schema evolution](/schemas#what-a-new-column-name-may-hold) added from a file header) is not refused, so the pipeline can be saved again unchanged. A new or renamed field, or one moved to the other schema, still follows the rule, and so does every `partitionBy` field. A save that changes the destination (another database engine, another object-store `fileFormat`, or an added destination) keeps such a name only when it passes the check a new header cell passes for that destination (no control character, the destination's length limit, no backtick on ORC); otherwise `400` with `Column name: <name> in the source schema cannot be kept for the new destination: ...`. The same check applies to version restore (against the live pipeline) and catalog restore.

**pgvector schema and table names:** for every caller, a new or changed pgvector `schemaName` or `tableName` with a double quote or a NUL character, or an empty `schemaName`, returns `400` with `The pgvector schema and table names must not contain double quotes, and the schema must not be empty. Choose plain names.`, and a pgvector destination with no `tableName` (missing or blank) returns `400` with `A pgvector destination needs a table name. Set destination.pgvector.tableName.` A save that keeps exactly the schema and table name the saved pipeline already has is not refused by this rule. Names are otherwise used exactly as written: case, spaces, dots and hyphens are kept. The same check applies to version restore and catalog restore.

**One pipeline per vector container:** a vector collection, class or table (pgvector: schema plus table) belongs to one pipeline. A save whose vector destination names a container another pipeline already uses returns `400` with an `error` naming the container, for example `The qdrant collection docs is already in use by another pipeline. ...`. The other pipeline is named only when you can see it. The same applies to the source-of-authority refusal (`... is already the authoritative writer of ...`) for every destination: a pipeline you cannot see is reported as `another pipeline`. A pipeline that already shared a container before this rule (an existing install) is not refused by this rule while its container is unchanged; the other save checks still apply, including the source-of-authority rule (two pipelines on one container need `authoritative: false` on one of them, as before). The same check applies to version restore and catalog restore.

**Destinations used by pipelines you cannot see:** if you cannot see every pipeline (a user with scoped catalog access, or an API key scoped by `catalog=` or `owner=self`), a save that points a pipeline at a table, collection, object-store prefix or topic that a pipeline you cannot see writes returns `400` with `The destination <kind>:<coordinates> is already in use by another pipeline. Choose another destination.`, whatever `authoritative` says; a pgvector table and a Postgres destination table with the same schema and name count as one table. A pipeline that already wrote that destination before saves again freely while its destination is unchanged. If the pipeline list cannot be read, such a save returns `500` and nothing is saved. Unrestricted users and full-access keys can still share a destination with `authoritative: false`. The same check applies to version restore and catalog restore.

**New destinations only (scoped users):** for a user with scoped catalog access (a restricted user's session), each new or changed Postgres, SQL Server, Snowflake or Databricks table, pgvector table, MongoDB collection, Qdrant, Milvus or Chroma collection, Weaviate class and object-store prefix is checked with the pipeline's own credentials (for Postgres and MongoDB, the platform's own connection; for pgvector, the pgvector connection the pipeline loads through and its delete drops with; for Qdrant, Weaviate, Milvus and Chroma, the store connection the platform loads, searches and deletes with) when the pipeline is saved. If it already exists (a Snowflake or Databricks table or view; for Postgres anything `SELECT * FROM "schema"."table"` can read, including views and materialized views, in the pipeline's database; for SQL Server any object `SELECT * FROM schema.table` can read, including views and synonyms; for MongoDB a collection or view of that exact name; for Qdrant a collection or alias of that exact name; for Weaviate a class or collection alias of that name in any letter case; for Milvus a collection of that name in the default database; for Chroma a collection of that exact name in the default tenant and database; any object under the prefix), the save returns `400` with `The destination <kind> <coordinates> already exists. Choose a table or prefix that does not exist yet, or ask a user with install-wide access to save this destination.` The message names only the coordinates in the request. A missing database, catalog or schema counts as not existing. A SQL Server table name that differs only in letter case is checked again, since a case-sensitive collation treats it as another table; on a case-insensitive database that check finds the pipeline's own table, so a case-only change of its own table name is refused too (an install-wide user can make it). When Unity Catalog sync state kept for the pipeline's name records a catalog commit (`catalogMode` managed or rest), a save returns `400` with `A pipeline of this name has an Iceberg table committed through Unity Catalog on record. Choose another pipeline name, or ask a user with install-wide access to save this destination.` if the pipeline is new and has an object-store destination of any format, or if it turns a stored pipeline into an object-store Iceberg one (including switching a pipeline back to Iceberg; a failed read of that state is the `500` below). Another prefix does not help; another pipeline name does. A rename of an object-store pipeline to such a name returns `409` `Pipeline '<name>' already exists. Choose another name.` A SQL Server table named `#...` or `##...` (a temporary table) returns `400` with `A SQL Server temporary table (a name starting with #) cannot be a pipeline destination. Choose another table name.` An object-store `prefixKey` or `destinationBucketOverride` with a wildcard or escape character (`* ? [ ] { } \`) or leading or trailing spaces, or a prefix with an empty, `.` or `..` segment, returns `400` with `The object-store prefix and bucket must be plain names: no wildcard or escape characters (* ? [ ] { } \), no leading or trailing spaces and no empty, '.' or '..' path segments. Choose a plain prefix.`; a new or changed Qdrant or Chroma collection name or Weaviate class name with a character other than letters, digits, `.`, `_` and `-`, or one that is `.` or `..`, or a new or changed Milvus collection name with a character other than letters, digits and `_`, one that does not start with a letter or `_`, or one longer than 255 characters, returns `400` with `A Qdrant or Chroma collection name or a Weaviate class name may use only letters, digits, '.', '_' and '-', and cannot be '.' or '..'; a Milvus collection name only letters, digits and '_', starting with a letter or '_', at most 255 characters. Choose a plain name.`, and one with no name (missing or blank) that the saved pipeline does not already have returns `400` with `A Qdrant, Milvus or Chroma destination needs a collection name, and a Weaviate destination a class name. Set collectionName or className.` (changing only the case of the first letter of a Weaviate class is not a change); the pgvector name rule above applies, and in addition a saved pipeline you cannot see keeps no pgvector schema or table name for you; for the same user, `POST /api/v1/query/objectstore` returns that `400` for a pipeline whose saved prefix is not a plain path, so such a pipeline saved earlier loses its preview for that user until its prefix is changed. If the check fails (the database, warehouse, bucket or vector store cannot be reached, a vector store is not configured on this install, gives an answer the check does not recognise or answers a collection list larger than 8 MB, an object-store endpoint does not answer within a few seconds (the check does not retry), the credentials are refused, or the whole check, including the Unity Catalog state read, does not finish within 30 seconds), the save returns `500` with `Could not check whether the destination already exists; nothing was saved. Try again.` Each user can have two checks running at once (a check abandoned at its deadline counts until it really ends): a save, version restore or rename that needs a check while two of the same user's are still running returns `429` with `Another destination check of yours is still running; nothing was saved. Wait a moment and try again.` and `Retry-After: 5`; nothing is started or saved. In a catalog restore that pipeline is reported as not restored with the same message. A rename's Unity Catalog state read gets 5 seconds (then the rename's `500`). Not checked: a save that keeps the stored destination and credentials, and a destination that a pipeline the user can see already uses with the same credentials (for an object store, the same prefix or one inside it; for a pgvector table, a pgvector pipeline the user can see on the same schema and table; the one-pipeline-per-vector-container rule above still applies to it). The same check applies to version restore and catalog restore. Unrestricted users and every API key, including scoped keys, are not checked.

**Version restore is checked like a save:** restoring a version (`POST /api/v1/pipeline/version/restore`, or Version History in the UI) gives the answer saving that version's configuration would give you today. Every check on this page applies, for every caller including admins: a version saved before a rule existed, or one that no longer fits the install (for example a table name that is not a plain identifier, a server-managed secret, two destination engines, a field protection method that is refused, a bucket outside the allowlist, a file-format or partitioning change over existing data, a second authoritative writer, or a Postgres destination where Postgres is not reachable), is refused with `400` and the same `{"error": "..."}` message as `POST /api/v1/pipeline`, and nothing is written. A restore brings back the definition only: the pipeline keeps its current name, catalog, owner and earlier names (to move a pipeline to another catalog, change its `catalog`; a deleted pipeline is restored into the version's catalog, keeping the version's owner). Restoring a deleted pipeline re-creates it, so it needs the right to create that pipeline (`pipeline:create`, in scope for a scoped key, on the version's catalog and owner) as well as `pipeline:update`; without it the restore answers `403` naming `pipeline:create` and nothing is written. Restoring over a pipeline that still exists needs `pipeline:update` only. If the pipeline is renamed, deleted, created or moved while the restore is being checked, it returns `409` (`Pipeline '<name>' changed while it was being restored; nothing was restored. Try again.`). To recover a refused version, open it (`GET /api/v1/pipeline/version`, or Version History), copy its configuration, fix the field the message names and save it with `POST /api/v1/pipeline`; the version history is not changed.

## Rename a Pipeline

```
POST /api/v1/pipelines/{name}/rename
```

Changes a pipeline's name and nothing else. Its destination data stays where it is, its definition version history and stored CodeGen scripts (with their history) move to the new name, an incremental database pull continues from where it was, and every tap whose target is the pipeline is pointed at the new name. The Pipelines tab's inline rename uses this endpoint.

**Body:**
```json
{"newName": "sales_data_v2"}
```

The new name is trimmed and can be up to 80 characters.

**Example:**
```bash
curl -X POST http://localhost:8080/api/v1/pipelines/sales_data/rename \
  -H "Content-Type: application/json" \
  -d '{"newName": "sales_data_v2"}'
```

**Response:** `200 OK`

```json
{
  "name": "sales_data_v2",
  "previousName": "sales_data",
  "version": 4,
  "repointedTaps": ["sales_tap"],
  "failed": [],
  "warnings": []
}
```

- `version` is the renamed pipeline's definition version; the rename is recorded as a new version with the note `renamed <old> -> <new> by <actor>`.
- `repointedTaps` lists the taps now pointing at the new name. Taps you cannot see are re-pointed too but never named.
- `failed` lists taps that could not be re-pointed (`{"name", "error"}`); the response is then `207 Multi-Status` and the pipeline is renamed anyway. Re-point those taps by editing them.
- `warnings` are follow-up notes, for example a CodeGen script that no longer matched its instruction and is generated again on the first run, or a repository file under the old name that was kept because it was edited by hand.

**Refusals (nothing is renamed):**

| Status | When |
|--------|------|
| `400` | `newName` missing, blank, unchanged or longer than 80 characters; or the pipeline syncs to Unity Catalog (its table there is named after the pipeline: create the pipeline under the new name instead) |
| `403` | You can see the pipeline but do not own it: renaming needs the same access as deleting (**own** on its catalog for a user with scoped access, `pipeline:delete` for an API key) |
| `404` | No such pipeline, or one you cannot see |
| `409` | A pipeline with the new name already exists (for a caller who cannot see every pipeline, also when the new name is an earlier name of a pipeline they cannot see), a job for the pipeline is queued or running, a stored CodeGen script could not be copied to the new name, or (for a user with scoped catalog access renaming an object-store pipeline) Unity Catalog sync state kept for the new name records a catalog commit |

If a rename stops part way (for example the server restarts), sending the same rename again finishes it. A pipeline that already has the new name and was not created by that rename is always a `409`, even if its configuration is identical.

What keeps the old name: run status and history, run lineage and provenance, audit entries, incidents and approvals, the `source_pipeline` recorded on chunks already in a vector store, older tap version snapshots, and scratch results already written. The renamed pipeline lists its earlier names, oldest first, in `previousNames`, a new read-only field stored with the pipeline's configuration and returned by `GET /api/v1/pipeline`. The server maintains it: a value sent in a `POST /api/v1/pipeline` body or found in a restored version is ignored (the stored list is kept; a new pipeline has none). Users with scoped catalog access keep seeing the pipeline's run history, provenance, lineage runs, activity and search results recorded under an earlier name. If another pipeline now carries that earlier name, records under it could belong to either pipeline, so a user with scoped catalog access sees them only when they can see all of those pipelines. Otherwise the name reads as if it had no runs: lineage and `find_data` freshness shows no last landing, record count or latest run ID, lineage edges carry no run evidence, datasets only those runs wrote are not shown, and AI-inferred column lineage stored under the name is not used. Unrestricted users and API keys see them as before. The audit log records the rename as `pipeline` / `rename` on the old name with `newName` in the details.

**Earlier names of pipelines you cannot see:** if you cannot see every pipeline (a user with scoped catalog access, or an API key scoped by `catalog=` or `owner=self`), you cannot take a name that a pipeline you cannot see had before it was renamed. Creating a pipeline under that name, restoring a deleted pipeline of that name from a version, or renaming a pipeline to it is refused the same way as if a pipeline you cannot see still had that name: a save or version restore returns `404` for a user with scoped catalog access and, for an API key, the same `403` as for a pipeline outside its scope (for a key whose read is scoped but whose create and update are not, a `403` on `pipeline:read`); a rename returns the taken-name `409` (`Pipeline '<name>' already exists. Choose another name.`). If the pipeline list cannot be read for this check, nothing is saved, restored or renamed (`500`). If a save by such a caller finds that the pipeline of that name was created, deleted, renamed or moved to another catalog while the save was being checked, nothing is saved and it returns `409` (`Pipeline '<name>' changed while it was being saved; nothing was saved. Try again.`), or the refusal it would now get; send it again.

## Delete a Pipeline

```
DELETE /api/v1/pipeline?pipeline={name}
```

**Parameters:**
| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `pipeline` | query | Yes | Pipeline name |
| `deleteData` | query | No | Delete destination data (default: `true`). `deleteData=false` (any letter case) together with the configuration delete keeps the destination data: see **Keep the data** below. With `deleteConfig=false`, `deleteData=false` deletes nothing. Any other value deletes the data. |
| `deleteConfig` | query | No | Delete pipeline configuration (default: `true`). Set to `false` to delete data only while keeping the pipeline config. |

**Keep the data:** `deleteData=false` without `deleteConfig=false` deletes the pipeline's configuration, its definition versions and its AI scripts, and leaves the Postgres, SQL Server, Snowflake or Databricks table, the MongoDB collection or the object-store files where they are. The `200` body then also carries `kept`, the tables, collections and prefixes left in place (an empty array when the pipeline wrote nothing that can be kept, such as a [Live Read](/destinations/live-read) pipeline, a Kafka topic, an ActiveMQ queue or a REST endpoint). No pipeline manages the kept data afterwards: nothing writes to it, and a later delete does not remove it. The document-tap ledgers of a tap feeding the pipeline are kept with the data, so a pipeline re-created under the same name does not ingest every document again; a Live Read pipeline's working folder is still deleted. For an Iceberg table committed through Unity Catalog, the table and its Unity Catalog state stay (see [Unity Catalog](/destinations/unity-catalog)). Keeping the data of a pipeline that writes to a vector store (pgvector, Qdrant, Weaviate, Milvus, Chroma) is refused with `400` and nothing is deleted: delete it with its data, or keep the pipeline. A user with scoped catalog access can keep data but cannot then point a pipeline at the kept table, collection or prefix: the save is refused because the destination already exists (see [Catalog access](/user-auth#catalog-access)).

**Examples:**
```bash
# Delete pipeline and all data
curl -X DELETE "http://localhost:8080/api/v1/pipeline?pipeline=sales_data"

# Delete data only, keep pipeline configuration
curl -X DELETE "http://localhost:8080/api/v1/pipeline?pipeline=sales_data&deleteData=true&deleteConfig=false"

# Delete the pipeline configuration, keep the destination data
curl -X DELETE "http://localhost:8080/api/v1/pipeline?pipeline=sales_data&deleteData=false"
```

**Response:** `200 OK` with a JSON body:

```json
{ "warnings": [] }
```

With `deleteData=false` (keep the data), the body also lists what was kept:

```json
{ "warnings": [], "kept": ["postgres table datris.public.sales_data"] }
```

`kept` is present only in that mode. Keeping the data of a vector-store pipeline returns `400 Bad Request` and deletes nothing:

```json
{ "error": "This pipeline writes to a vector store; its configuration cannot be deleted while keeping that data. Delete it with its data, or keep the pipeline." }
```

`warnings` lists anything left for you to handle. For an object-store Iceberg pipeline whose table was committed through Unity Catalog (`catalogMode: rest`), it says `Unity Catalog still holds <catalog>.<schema>.<table>; have an admin drop it`, because Datris removes the files but never drops the catalog table (see [Unity Catalog](/destinations/unity-catalog)). For a `catalogMode: managed` table it says `Unity Catalog owns <catalog>.<schema>.<table> and its files (catalogMode managed); Datris deleted nothing there; drop <catalog>.<schema>.<table> in Unity Catalog to remove the data`.

A vector collection, class or table that another pipeline also names is not dropped: the pipeline's own config is deleted, the container and its chunks stay with the other pipeline, and `warnings` holds `Kept <store> <collection|class|table> <name>: ...` (naming the other pipeline only when you can see it). The container is dropped with the last pipeline that names it. A pgvector pipeline saved without a `tableName` (possible in earlier versions) never has its table dropped: `warnings` says the table was not dropped, and it can be dropped in PostgreSQL by hand. A data-only reset (`deleteConfig=false`) does not clear a shared container either: its chunks stay, and the document-tap ledgers of a tap feeding the pipeline are kept too, so the next tap run does not ingest every document again into the shared container.

A Qdrant, Milvus or Chroma collection or a Weaviate class that the store could not remove (the store is down, refuses the delete, does not answer within 5 seconds, answers with an error, or is not configured on this install) is reported in `warnings` as `Could not remove <store> collection|class <name>: <reason>.`, followed by `Its pipeline configuration was deleted; remove it in the store.` on a delete or `Run the reset again once the store is available.` on a data-only reset. The reason is one of `the store is not configured`, `the store could not be reached`, `the store did not answer in time`, `the store answered HTTP <code>` or `the store reported an error`; after `the store did not answer in time` the warning adds `The removal may still complete in the store; check it there.`, because a large removal can outlast the wait and still finish; the store's own answer is written to the server log only. The delete still answers `200` and deletes the configuration, so the collection is left with no pipeline until it is removed in the store. A data-only reset whose drop failed keeps the document-tap ledgers of a tap feeding the pipeline, so the next tap run does not ingest every document again into the collection that is still full. A collection the store reports as already gone is not a failure. The catalog delete cascade reports the same warning per pipeline.

A Postgres, SQL Server, Snowflake or Databricks table, a MongoDB collection, a pgvector table, an object-store prefix or the scratch folder that could not be removed is reported the same way: `Could not remove <label>: <reason>.` (for example `Could not remove postgres table datris.public.sales_data: the store could not be reached.`), then the same closing sentence as for a vector collection. The reason is one of `the store is not configured` (its secret or credentials secret is missing or incomplete, including a pgvector install with no pgvector secret), `the store could not be reached`, `the store did not answer in time`, `the store refused the credentials`, `the store refused permission to remove it` or `the store reported an error`; the store's own message, the SQL, hosts and secret names go to the server log only. An object store that denies the delete is always reported as `the store refused permission to remove it`, because it cannot tell rejected credentials from a denied action. A store answer that could mean "missing" or "not allowed" (a Snowflake database that "does not exist or is not authorized", a SQL Server database the login cannot open) is reported as `the store reported an error`, since the table may still be there. A table, database, schema, collection or prefix that is already gone is not a failure.

Each of these removals is bounded: connecting, signing in and the drop itself each get 30 seconds on Postgres, pgvector, MongoDB, SQL Server, Snowflake and Databricks. A drop still waiting after that (for example behind a long-running load that holds a lock on the table) ends with `the store did not answer in time`; a Postgres or pgvector drop cut off this way is rolled back, so the table is not dropped later behind your back. Object-store and scratch deletes keep the object store's own timeouts and retries, so an unreachable object store can still take several minutes before its warning appears.

A data-only reset (`deleteConfig=false`) whose table, collection, prefix or vector collection could not be removed keeps the document-tap ledgers of a tap feeding the pipeline, so the next load does not add to the rows still there; a scratch folder or stored history that could not be removed does not count. An object-store prefix that overlaps another pipeline's prefix is not deleted and `warnings` holds `Kept object-store prefix <bucket>.<prefix>: another pipeline also writes to it.` A full delete also reports document-tap ledgers, stored history, stored CodeGen scripts or Unity Catalog sync state of the pipeline that could not be removed. If the configuration itself cannot be deleted after the data was removed, the delete answers `500` with `The pipeline's destination data was already removed; the configuration could not be deleted. Run the delete again.` The catalog delete cascade reports every one of these warnings per pipeline.

A Postgres destination table is never dropped when its `dbName`, schema or table name does not meet the naming rule (only `a-z`, `A-Z`, `0-9` and `_`, not empty, at most 63 bytes). In a multi-tenant install the tenant database is used instead of `dbName`; the character rule does not apply to it, and only an empty tenant database name, one holding a NUL character or one longer than 63 bytes counts as failing (schema and table are still checked in full). This also holds for a data-only reset: no connection is made for it, the rest of the delete goes ahead, and `warnings` holds `The PostgreSQL table was not dropped because its name does not meet the naming rule (...); drop it in PostgreSQL if it is no longer needed.` Such a table can only come from a pipeline saved before the rule applied to it.

In the same way, a Postgres, SQL Server, Snowflake or Databricks table or a MongoDB collection that another pipeline also writes to (including a pgvector table and a Postgres destination table with the same schema and name) is not dropped, also for a data-only reset: `warnings` holds `Kept <kind> table|collection <name>: ...` (naming the other pipeline only when you can see it), and the table is dropped with the last pipeline that writes to it. The catalog delete cascade reports the same warnings per pipeline.

## Authentication

If `useApiKeys` is enabled, all requests must include the `x-api-key` header:

```bash
curl -H "x-api-key: your-api-key" http://localhost:8080/api/v1/pipelines
```

API keys are stored in Vault under `{environment}/api-keys` (`oss/api-keys` on a default install). `secrets.apiKeysSecretName` in `application.yaml` tells the validator where to read them and should point at that same path — the Keys UI and multi-tenant resolution always write to `{environment}/api-keys`.
