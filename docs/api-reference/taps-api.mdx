## List Taps

```
GET /api/v1/taps
```

Returns all registered taps.

**Response:** JSON array of tap configurations.

## Get Tap

```
GET /api/v1/tap?name={tapName}
```

Returns a single tap configuration plus the Python script body from MinIO.

**Parameters:**
| Parameter | Type | Description |
|---|---|---|
| `name` | query | Tap name (required) |

**Response (success):**
```json
{
  "name": "stock-prices-tap",
  "description": "Fetch daily stock prices from yfinance",
  "scriptPath": "tap-scripts/stock-prices-tap_a1b2c3d4.py",
  "targetPipeline": "stock-prices-pipeline",
  "script": "def fetch():\n    ...",
  "packages": ["yfinance"],
  "enabled": true,
  "tapType": "structured",
  "state": {"cursor": "2026-04-20"},
  "stateUpdatedAt": "2026-04-20 14:05:00 UTC"
}
```

`state` and `stateUpdatedAt` appear only once the tap has committed incremental-sync state (see [Incremental Sync](/taps#incremental-sync-state)); they carry the current cursor so a caller can read it without a separate request.

**Response when the stored script is missing from object storage:**
```json
{
  "name": "stock-prices-tap",
  "scriptPath": "tap-scripts/stock-prices-tap_a1b2c3d4.py",
  "script": null,
  "scriptMissing": true,
  ...
}
```

`scriptMissing` only appears when `scriptPath` is set but the object is absent — typically after an interrupted edit or re-generation wiped the old script before the new one landed. Distinguish from "never generated" (`scriptPath` null, `script` null, no `scriptMissing` key). The Edit Tap UI uses this flag to render a recoverable-state banner instead of the generic "Generate a script first" validation.

## Create or Update Tap

```
POST /api/v1/tap?changeNote={note}
Content-Type: application/json
```

**Query parameters:**
| Parameter | Type | Description |
|---|---|---|
| `changeNote` | query | Optional. Free-text note stored as `changeNote` on the definition version this save creates. Shown in `GET /api/v1/tap/versions` and in the Versions panel of the UI. |

**Body:**
```json
{
  "name": "stock-prices-tap",
  "description": "Fetch daily stock prices from yfinance",
  "scriptPath": "tap-scripts/stock-prices-tap_a1b2c3d4.py",
  "targetPipeline": "stock-prices-pipeline",
  "packages": ["yfinance"],
  "secretName": "my-api-creds",
  "cronExpression": "0 0 0 * * ?",
  "enabled": true,
  "tapType": "structured"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `tapType` | string | `"structured"` | `"structured"` or `"document"`. Document taps return `{uri, filename, content}` dicts and require a `targetPipeline` with an `unstructuredAttributes` source and a vector-store destination. Cannot be changed once set. |
| `catalog` | string | `null` | Free-form label that groups related taps and pipelines in the [Data Catalog](/data-catalog). Empty or null = Uncataloged. |

**Document-tap compatibility rule.** When `tapType == "document"` and `targetPipeline` is non-empty, the server validates that the pipeline has:

- `source.fileAttributes.unstructuredAttributes != null`
- A vector-store destination (one of `qdrant`, `pgvector`, `weaviate`, `milvus`, `chroma`)

Mismatches return **HTTP 400** with a message naming the violation. Also enforced at run time in `TapRunner.feedDocumentPipeline` in case the pipeline is reshaped after the tap is saved.

**Test-before-cron rule (HTTP 409).** A tap may only carry a `cronExpression` once the exact script (or, for HTTP taps, the exact `endpointUrl`) that will run on that schedule has passed a test run (`POST /api/v1/tap/run` with `mode: "test"`). The save is refused with **HTTP 409** and nothing is persisted (no new version is minted) when either:

- the `cronExpression` is being set or changed and the stored tap has no successful test for the script being saved, or
- the `cronExpression` is unchanged but the script (new `scriptPath` / `scriptCommitSha` / `endpointUrl`) differs from the one that last passed a test.

```json
{
  "error": "Tap 'stock-prices-tap' cannot be scheduled: its script has never passed a test run. Remedy: save the tap without `cronExpression`, call `test_tap`, then `update_tap` with the cron."
}
```

Remedy, in order: save the tap **without** `cronExpression`; run it with `mode: "test"` until it succeeds (the server stamps the tested script on the tap as `lastTestRunScriptId`); then save again with the `cronExpression`. Clearing a cron, and cadence-only or metadata edits (description, tags, `targetPipeline`, `enabled`) on a tap whose current script has passed a test, are always accepted. Test state is read from the stored tap only — `lastTestRun*` fields in the request body are ignored. Pre-existing scheduled taps keep running and stay editable; the first cron or script change on such a tap is accepted if the tap has ever tested or run successfully, otherwise it needs a test run first. The same rule applies to `POST /api/v1/tap/version/restore`. `POST /api/v1/tap/script` applies the rule up front: storing different bytes for a tap that currently has a `cronExpression` is refused with the same **HTTP 409** body before anything is written to the object store or code repository (so the repository never drifts ahead of the tap's pinned commit). Clear the cron first (save with `cronExpression: null`), then store, test, and set the cron. Storing identical bytes, or storing for an unscheduled tap, is always accepted. The AI script endpoints (`/tap/generate`, `/tap/fix`, `/tap/review`, `/tap/optimize`) still return the new script and its `scriptPath` with HTTP 200, but do not move a scheduled tap onto the new bytes; when that happens the body also carries the gate message under `error`.

**Who the AI script endpoints change a tap for.** `/tap/generate`, `/tap/fix`, `/tap/review` and `/tap/optimize` point a stored tap at the new script only when the request names that tap (`tapName` present and not blank) and the caller may update it: it holds `tap:update` or `tap:create` on the tap's catalog and owner (and may read the tap), or is a user whose role or catalog grant allows editing it. A caller that may read the tap but not update it (a viewer, or a key such as the read-only, reporting or ops template) gets the same HTTP 200 and the new script, the stored tap, its versions and its test state are left as they were, and the body carries `"error": "The stored tap was left unchanged: this caller may not update it"`. A request with no `tapName`, or a blank one, never reads or changes a stored tap, whatever taps exist, so a user limited to catalogs gets the review or optimization of such a request rather than `404`.

**Script references for callers limited to a catalog or to what they created.** For a user limited to catalogs, or an API key limited to a catalog or to what it created, a new or changed `scriptPath` or `scriptRepoPath` must be a tap script: an object under `tap-scripts/` on built-in storage, or a file under the code repository's path prefix and outside its `pipelines/` folder, with no empty, `.` or `..` path segment (so no leading, trailing or doubled `/`). It must also not be the current script of a tap that caller cannot see, however the path is written. Otherwise nothing is saved, and the answer is the one a tap outside the caller's access gets: `404` `Tap: <name> not found` (the tap being saved) for such a user, `403` naming `tap:read` for a key, the same for both reasons and naming nothing of another tap. A reference left as stored, or left out of the body (the stored one is kept), is never refused by this rule; the tap editor, the MCP tools and renaming produce references it accepts. In this release the rule applies to those callers only, and version restore is reported rather than refused; a later release applies the tap script area to every caller's references.

**Version restore is checked like a save:** restoring a version (`POST /api/v1/tap/version/restore`, or Version History in the UI) gives the answer saving that version's configuration would give you today. Every check on this page applies, for every caller including admins: a version whose secret may not be used by a tap, whose `scriptKind` is unknown, whose HTTP endpoint is missing or invalid, whose script is no longer in its storage backend, whose document target pipeline cannot take documents, whose changed `dependsOn` names a tap outside the catalog or closes a cycle, or whose cron is invalid or fails the test-before-cron rule, is refused with the same status and `{"error": "..."}` message as `POST /api/v1/tap`, and nothing is written. A restore brings back the definition only (script reference, kind, endpoint, packages, secret, cron, target, tags, source, dependencies): the tap keeps its current name, catalog, owner, enabled state, and run, retry and test state. To move a tap to another catalog, change its `catalog`; to turn its schedule on or off, save it with `enabled`. A deleted tap is re-created as `POST /api/v1/tap` creates one, so restoring it needs the right to create that tap (`tap:create`, in scope for a scoped key, on the version's catalog with you as owner) as well as `tap:update`; without it the restore answers `403` naming `tap:create` and nothing is written. The re-created tap is in the version's catalog, owned by you, with its test status cleared (so a schedule must pass a test run again before it can be set); its other recorded run details are as they are in the version. If the tap is created, deleted, moved, given another owner, or enabled or disabled while the restore is being checked, it returns `409` (`Tap '<name>' changed while it was being restored; nothing was restored. Try again.`). To recover a refused version, open it (`GET /api/v1/tap/version` returns its configuration and script text, or Version History), fix the field the message names, store the script again if needed (`POST /api/v1/tap/script`) and save it with `POST /api/v1/tap`; the version history is not changed.

## Delete Tap

```
DELETE /api/v1/tap?name={tapName}
```

Deletes the tap configuration and its script. For document taps, also clears the ledger entries and deletes all staged MinIO objects for that tap.

Only the tap's own script file is deleted (on built-in storage the object the platform wrote for the tap; in a [code repository](/tap-github-storage#which-file-a-tap-owns) `<path prefix><tap name>.py` under the current or a recorded earlier path prefix), and only when no other tap uses the same file. On built-in storage a script object the platform wrote for the tap under another name (a tap renamed before its first save) is also deleted when no tap has that name and no other tap uses it. Any other file the tap points to is left in place; the tap is still deleted. The same rules apply to the script objects of the tap's earlier versions. In a code repository a file edited since the tap's recorded commit is also kept.

**Response:**
```json
{
  "message": "Tap deleted: stock-prices-tap",
  "warnings": [
    "The tap's script file was left in place because it is not a file this tap alone owns; remove it by hand if it is no longer wanted."
  ]
}
```

`warnings` is empty when the script file was deleted. Each kept file gives one warning: the text above for a file that is not the tap's own or is still used by another tap (also when the list of taps could not be read), or a message naming a repository file that was edited since its recorded commit, could not be checked, or whose delete could not be confirmed. Deleting a catalog with its items reports the same warnings per tap.

## Change Owner

```
POST /api/v1/tap/owner
Content-Type: application/json
```

Hands an existing tap to another user or API key. The tap keeps its versions, incremental-sync state, document ledger, run history, schedule, enabled state and script; only its owner changes. A tap's owner is otherwise set when it is created and kept on every later save: an owner named in the body of `POST /api/v1/tap`, a version restore or a catalog restore is ignored.

Only an administrator (a signed-in admin, or an API key with full access: unscoped `*:*` or a legacy key) may change a tap's owner. Every other caller, including a key holding `tap:update` or a wildcard limited to a catalog or to what it created, gets `403` `Changing a tap's owner needs an administrator or a full-access API key`, and nothing about the tap is read.

**Body:** the tap and exactly one of `user` or `key`.
```json
{
  "name": "stock-prices-tap",
  "key": "sales-agent"
}
```
```json
{
  "name": "stock-prices-tap",
  "user": "ed"
}
```

- `user` names a user; the tap is stored as owned by `session:<username>`.
- `key` names an issued API key by its label. A revoked or unknown key is refused. The platform's own identities (`anonymous`, `recovery-agent`, `system`, `agent`) and labels starting `session:` or `tap:` cannot be named; `ui` can, when it is an issued key.

With an API key that has full access:
```bash
curl -s -X POST http://localhost:8080/api/v1/tap/owner \
  -H "x-api-key: $DATRIS_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "stock-prices-tap", "key": "sales-agent"}'
```

With [user authentication](/user-auth) on and API keys off, sign in as an admin and send the `datris-session` cookie your sign-in set:
```bash
curl -s -X POST http://localhost:8080/api/v1/tap/owner \
  -b "datris-session=$DATRIS_SESSION" \
  -H "Content-Type: application/json" \
  -d '{"name": "stock-prices-tap", "user": "ed"}'
```

**Response:**
```json
{
  "name": "stock-prices-tap",
  "owner": "sales-agent",
  "previousOwner": "session:ada",
  "changed": true,
  "warnings": []
}
```

`changed` is `false`, and nothing is written, when the tap already has that owner.

**Who may own the tap.** An administrator, a user with no catalog limits who may edit taps, or a key with full access can always be the owner. Any other new owner is refused with `409` and a message saying what to do, and nothing changes, when:
- it could not edit the tap where it is: it cannot see the tap's catalog, or may not change taps (a viewer, a read-only key); or
- it may not load into the tap's target pipeline.

Grant the new owner what it lacks, point the tap at a pipeline it may load into, or pick another owner. Findings that `datris doctor` reports but that do not decide this change are returned in `warnings`, in the words of the [`tap.owner_scope` and `tap.references` rows](/doctor#the-checks), and the owner is still changed: a target pipeline that does not exist yet, callback reads the new owner's access narrows, and a tap secret outside the new owner's tap access.

**Other answers.** `400` when the body names both or neither of `user` and `key`, an unknown user, an unknown, revoked or reserved key, or a catalog placeholder. `404` (`Tap: <name> not found`) for a missing tap. `409` (`Tap '<name>' changed while its owner was being changed; nothing was changed. Try again.`) when the tap was moved to another catalog or pointed at another pipeline while the change was being checked.

**What changes at once.** The owner decides which keys limited to what they created (`owner=self`) reach the tap: from the change on, the new owning key may read and update the tap and the previous owning key may not. The owner also shows in data lineage and in `datris doctor`'s tap rows (which may take up to 15 seconds to catch up). Nothing else a tap does changes in this release (see [Who a tap runs as](/taps#who-a-tap-runs-as)).

**What does not change.** No tap version is written and the tap's update time is kept, so its version history, last editor and schedule are as they were. A run or test in progress finishes as it started and does not put the previous owner back; the next run reads the new owner. Each change is recorded in the [audit log](/audit-log#what-is-recorded) as `tap` / `owner-change` with the previous and new owner, and in the server log.

## Brainstorm (AI Chat)

```
POST /api/v1/tap/brainstorm
Content-Type: application/json
```

Multi-turn conversational endpoint that helps the user refine a vague tap idea into a clear instruction. The UI calls this on every message in the brainstorm chat panel of the tap creation wizard. The AI:

- Asks one focused clarifying question at a time
- Suggests specific data sources (e.g., yfinance, Alpha Vantage, Open-Meteo)
- Recognizes Datris platform tables and uses the metadata/query endpoints
- Returns an updated **instruction draft** on every turn so the UI can keep the instruction box in sync
- Returns **suggestedEnvVars** when an external API requires authentication

**Body:**
```json
{
  "messages": [
    {"role": "user", "content": "I'm looking for company earnings data"},
    {"role": "assistant", "content": "Which companies?..."},
    {"role": "user", "content": "Tickers from the consumer_discretionary_earnings table on Datris"}
  ],
  "currentDescription": "Optional: the current draft instruction so the AI has context",
  "tapType": "structured"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `tapType` | string | `"structured"` | Selects the system prompt. `"document"` uses a document-tap-aware prompt that asks about document sources (SharePoint, S3, URL listings, etc.) and never asks about chunking, embedding, or vector-store details (those are pipeline concerns). |

**Response:**
```json
{
  "reply": "Got it. Which earnings data source — yfinance (free), Alpha Vantage, or Polygon.io?",
  "description": "Query the consumer_discretionary_earnings table via /api/v1/query/postgres to get the ticker list. (Source TBD.)",
  "suggestedEnvVars": [],
  "injectedPrompts": []
}
```

After the user picks Alpha Vantage, a subsequent call returns:
```json
{
  "reply": "Good choice. The script will need an Alpha Vantage API key — please create a tap secret with ALPHA_VANTAGE_API_KEY in the credentials section below.",
  "description": "Query the consumer_discretionary_earnings table via /api/v1/query/postgres to get tickers, then for each ticker call the Alpha Vantage EARNINGS endpoint and return historical earnings records. Use os.environ.get('ALPHA_VANTAGE_API_KEY') for authentication.",
  "suggestedEnvVars": ["ALPHA_VANTAGE_API_KEY"]
}
```

The AI never suggests `DATRIS_POSTGRES_DATABASE`, `DATRIS_MONGODB_DATABASE`, `DATRIS_PLATFORM_HOST`, or `DATRIS_PLATFORM_PORT` in `suggestedEnvVars` — those are always injected by the platform.

## Generate Script (AI)

```
POST /api/v1/tap/generate
Content-Type: application/json
```

Uses AI to generate a Python `fetch()` script from a plain-English description. The system prompt branches on `tapType` — document taps get instructions to return `{uri, filename, content}` dicts and a different set of rules (no chunking, no embedding, no local-filesystem fallback).

**Body:**
```json
{
  "description": "Discover all PDFs in the S3 bucket 'contracts' under prefix 2026/",
  "tapName": "contracts-tap",
  "oldScriptPath": "tap-scripts/old_script.py",
  "secretName": "aws-creds",
  "tapType": "document"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `tapType` | string | `"structured"` | Selects the system prompt. Set to `"document"` when generating a document-tap script. |

**Response:**
```json
{
  "script": "import requests\n\ndef fetch():\n    ...",
  "packages": ["yfinance"],
  "scriptPath": "tap-scripts/stock-prices-tap_a1b2c3d4.py",
  "injectedPrompts": ["rate-limits"],
  "provider": "anthropic",
  "model": "claude-opus-5-5"
}
```

`injectedPrompts` lists the names of the [tap prompt fragments](#tap-prompt-fragments) that were injected into the generation prompt (empty when none matched). `provider` and `model` name the AI provider and model that generated the script.

## Generation Progress

```
GET /api/v1/tap/generate/status?tap={tapName}
```

Reports what a blocking `POST /api/v1/tap/generate` call for this tap is currently doing, so a client can show real progress during the 1–3 minute wait. Poll every few seconds while a generate request is in flight.

**Parameters:**
| Parameter | Type | Description |
|---|---|---|
| `tap` | query | Tap name the generate call was made for (required) |

**Response (generation in flight):**
```json
{
  "active": true,
  "phase": "calling-model",
  "attempt": 1,
  "elapsedSeconds": 42,
  "phaseElapsedSeconds": 42,
  "provider": "anthropic",
  "model": "claude-opus-5-5"
}
```

| Field | Description |
|---|---|
| `active` | `false` when no generation is running for this tap; the other fields are then omitted |
| `phase` | `calling-model`, `retrying-format` (the model's output failed the format check and is being re-requested) or `storing` |
| `attempt` | 1-based attempt counter |
| `elapsedSeconds`, `phaseElapsedSeconds` | Seconds since the generation started, and since the current phase started |
| `provider`, `model` | The AI provider and model handling the generation |

**Response (idle):** `{"active": false}`

**Body:**


## Store Script

```
POST /api/v1/tap/script
Content-Type: application/json
```

Stores a (typically hand-edited) Python script and, when the tap already exists, repoints the tap at it. The storage backend is resolved in order: an explicit `storage` in the body, else the existing tap's current backend (an existing tap never switches silently), else the tenant default — the [code repository](/tap-github-storage) when one is enabled, built-in object storage otherwise.

**Body:**
```json
{
  "tapName": "stock-prices-tap",
  "script": "import requests\n\ndef fetch():\n    ...",
  "storage": "github",
  "baseCommitSha": "9fceb02a1c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `tapName` | string | Yes | Tap identifier. The tap does not have to exist yet; storing for a new name only writes the script and returns its reference. |
| `script` | string | Yes | Python script body to store. |
| `storage` | string | No | Explicit backend: `minio` (built-in object storage) or `github` (code repository). |
| `baseCommitSha` | string | No | Repository storage only — the commit the editor loaded the script at. If the file changed in the repository since, the write is refused with **HTTP 409** instead of overwriting it. |
| `oldScriptPath` | string | No | Ignored. An existing tap's previous object is replaced from the tap's stored script reference. |

**Response:**
```json
{
  "scriptPath": null,
  "storage": "github",
  "scriptRepoPath": "taps/stock-prices-tap.py",
  "scriptCommitSha": "b7e23ec29af22b0b4e41da31e868d57226121c84"
}
```

`scriptPath` is set for built-in storage; `scriptRepoPath` and `scriptCommitSha` for the repository. Replacing an existing tap's script is a definition edit and lands as a new definition version (`GET /api/v1/tap/versions`) naming who made it; storing identical bytes is a plain write.

**Errors:** **HTTP 409** when `baseCommitSha` is stale (pull the latest, reapply the edit, retry), or when the tap carries a `cronExpression` and the new bytes have not passed a `mode=test` run — the test-before-cron rule, evaluated before anything is written (see [Create or Update Tap](#create-or-update-tap)). **HTTP 409** also when the script would be written to the code repository at `<path prefix><tapName>.py` for a name with no repository script of its own yet (a new name, or a tap moving into the repository with `storage: "github"`) and another tap already runs its script from that file: nothing is written, and the other tap's script is never replaced; use another tap name. A user limited to catalogs, or a key limited to a catalog or to what it created, gets in that case the answer a refused script reference gives on save (`403` naming `tap:read` for a key, `404` for a user). A tap that already stores its script in the repository at its own path keeps storing it there. **HTTP 409** also when a user limited to catalogs, or a key limited to a catalog or to what it created, uploads the script of a tap stored in the repository whose stored path is not its own file (see below): nothing is written, and the message names only that tap and asks for an administrator to move the script to the tap's own path. **HTTP 500** when `tapName` or `script` is missing.

A tap stored in the repository whose stored path is not its own file (for example a hand-placed path, or a path under an earlier prefix that is not recorded) still stores its script at that path in this release when an administrator, an editor without catalog limits or an unrestricted key uploads it; the server log and the [audit log](/audit-log#what-is-recorded) note it once a day, and `datris doctor` lists it under [`tap.references`](/doctor#the-checks). The same upload by a limited user or key is refused (`409`, above) and recorded in the audit log each time. A later release stores such a tap's next script at its own path and points the tap at it. A script stored under a name with no saved tap by a key that holds no `tap:create` is noted the same way; a later release refuses it.

## Pull Script from Repository

```
POST /api/v1/tap/script/pull
Content-Type: application/json
```

For a repository-backed tap, re-reads the script file at the configured branch head and reports whether it differs from the content at the tap's pinned commit. Drift is decided by comparing the file's content, not the commit shas — another tap's save moves the shared branch head without touching this file. With `apply: "true"`, a drifted tap is advanced to the head commit as a versioned edit (`pulled external repo edits (<sha>)`).

**Body:**
```json
{
  "tapName": "stock-prices-tap",
  "apply": "true"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `tapName` | string | Yes | Tap identifier. Must store its script in the code repository. |
| `apply` | string | No | `"true"` to move the tap's pinned commit to the branch head when drifted. Anything else only reports. |

**Response:**
```json
{
  "found": true,
  "drifted": true,
  "headCommitSha": "0c1d2e3f4a5b6c7d8e9f0a1b2c3d4e5f6a7b8c9d",
  "pinnedCommitSha": "b7e23ec29af22b0b4e41da31e868d57226121c84",
  "script": "import requests\n\ndef fetch():\n    ...",
  "applied": true
}
```

| Field | Description |
|---|---|
| `found` | `false` when the file no longer exists at the branch head (then `drifted` is `false` and nothing else is returned) |
| `drifted` | The branch-head content differs from the pinned commit's content. An unreadable pin counts as drifted so the caller still gets a runnable copy |
| `script` | Present only when drifted — the branch-head source |
| `applied` | Present only when drifted and `apply` was `"true"` |

**Errors:** **HTTP 500** with `{"error": ...}` when the tap does not exist or does not store its script in a code repository.

## Migrate Script Storage

```
POST /api/v1/tap/migrate-storage
Content-Type: application/json
```

Moves a tap's script between backends: reads it from the current backend, writes it to the target, and saves the tap as a versioned edit (`moved script storage to <target>`). Idempotent — a tap already on the target is returned unchanged. Built-in objects are never deleted on migrate-out, because version snapshots still pin them.

**Body:**
```json
{
  "tapName": "stock-prices-tap",
  "target": "github"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `tapName` | string | Yes | Tap identifier. |
| `target` | string | Yes | `github` (code repository) or `minio` (built-in object storage). |

**Response:** The migrated tap configuration (same shape as [Get Tap](#get-tap), without `script`), with `scriptStorage`, `scriptPath`, `scriptRepoPath` and `scriptCommitSha` updated.

**Errors:** **HTTP 400** with `{"error": ...}` for an unknown tap, an invalid `target`, or a tap whose current script cannot be read. **HTTP 409** with `{"error": ...}` for a move to `github` when another tap already runs its script from `<path prefix><tapName>.py`: nothing is written (a limited user or key gets the answer a refused script reference gives on save).

## Test Tap

```
POST /api/v1/tap/test?testLimit={N}
Content-Type: application/json
```

Executes the tap script without sending data to a pipeline. Returns results, logs, and AI diagnosis if issues detected.

For a user limited to catalogs, or an API key limited to a catalog or to what it created, the script reference follows the rule `POST /api/v1/tap` applies ([Script references for callers limited to a catalog or to what they created](#create-or-update-tap)): a new or changed reference outside the tap script area, or to the current script of a tap the caller cannot see, is refused before anything runs, with the same `404` or `403` a save gets.

**Query parameters:**

| Name | Type | Description |
|------|------|-------------|
| `testLimit` | integer (optional) | When `> 0`, the runner injects `DATRIS_TAP_TEST_LIMIT=<N>` into the script process. Well-written tap scripts honor this env var to cap their source reads and iteration loops, making tests faster and lower-cost. Cron runs and `mode=run` runs never set this — production runs always read every row. (A `/tap/run` call with `mode=test` caps at 20 records by default; see [Run Tap](#run-tap).) The UI's "Limit test sample to 20 records" checkbox in Create Tap → step 2 sends `testLimit=20`. |

**Body:** A TapConfig JSON object (same as Create).

**Structured response** (`dataType: "csv"` shown):
```json
{
  "records": [{"ticker": "AAPL", "close": 255.92}, ...],
  "recordCount": 503,
  "dataType": "csv",
  "columns": ["ticker", "date", "open", "high", "low", "close", "volume"],
  "logs": "Retrieved 503 tickers...\nBatch 1/11...",
  "error": null,
  "aiExplanation": null,
  "durationMs": 12400
}
```

**Document-tap response** (`dataType: "document"`):
```json
{
  "records": [
    {
      "uri": "s3://contracts/2026/acme-msa.pdf",
      "filename": "acme-msa.pdf",
      "content": "JVBERi0xLjQKJe…",
      "content_hash": "2f1c…",
      "metadata": {"source": "s3"}
    }
  ],
  "recordCount": 1,
  "dataType": "document",
  "columns": null,
  "logs": "Listed 1 object in s3://contracts/2026/",
  "error": null,
  "durationMs": 3100
}
```

If errors or 0 records are detected, `aiExplanation` contains an AI-generated diagnosis. `durationMs` is the end-to-end test wall time in milliseconds — this is what the [Optimize Script](#optimize-script) endpoint uses as the baseline timing for its perf rewrite.

For `dataType: "csv"`, **column names in `columns` and the keys inside each record in `records` are normalized** by the platform: lowercase, `[a-z0-9_]` only, with `%` rewritten to `percent`. Source data with names like `EPS Estimate` or `Surprise(%)` will appear as `eps_estimate` and `surprise_percent`. JSON/XML results destined for MongoDB are not normalized. See [Schema Definition → Column Naming Rules](/schemas#column-naming-rules). Document-tap records pass through unchanged — the platform never rewrites URI, filename, content, or metadata keys.

## Review Script (Post-Run)

```
POST /api/v1/tap/review
Content-Type: application/json
```

After a successful test, asks the LLM to scan the script's captured stderr/stdout for signals that the script *itself* should change — not for performance. The reviewer looks for rate-limit / throttle / burst warnings, deprecation hints, pagination / partial-response cues, and schema-drift / auth warnings. When a signal is found, the script is regenerated with the appropriate fix (add `time.sleep`, switch to the recommended endpoint, add pagination, update parsing for renamed fields) and persisted to MinIO as a new version. When no signal is found, the script is returned unchanged.

The UI invokes this automatically **before** [Optimize Script](#optimize-script) — if the reviewer rewrites the script, the optimizer is skipped on that pass (correctness from output outranks speed). Callers integrating directly should follow the same order: call `/tap/review` first, re-test on `rewritten=true`, and only call `/tap/optimize` when `rewritten=false`.

**Body:**
```json
{
  "tapName": "stock-prices-tap",
  "script": "current working script content...",
  "recordCount": 503,
  "durationMs": 298000,
  "logs": "Retrieved 503 tickers...\nSource warning: Burst pattern detected...",
  "oldScriptPath": "tap-scripts/stock-prices-tap_v3.py"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `tapName` | string | Tap identifier. Used for script path versioning. |
| `script` | string | The current working script that passed its test. |
| `recordCount` | integer | How many records the last test returned. |
| `durationMs` | integer | Wall time of the last test run in ms (from `/tap/test` response). |
| `logs` | string | Captured script stderr/stdout — the reviewer matches signals liberally against this text. |
| `oldScriptPath` | string | MinIO path of the current script. If rewritten, the new script is stored as a new version and the old path is retained for rollback. |

**Response:**
```json
{
  "script": "regenerated Python 3 script...",
  "packages": ["extra-package"],
  "scriptPath": "tap-scripts/stock-prices-tap_v4.py",
  "changes": [
    "Added 0.25s sleep between API calls — source reported burst pattern (5 rps limit)",
    "Lowered max_workers from 10 to 3"
  ],
  "rewritten": true
}
```

When `rewritten` is `true`, the stored tap named by `tapName` is pointed at the new script only for a caller that may update it; otherwise the body also carries `"error": "The stored tap was left unchanged: this caller may not update it"` and the stored tap is not changed (see [Who the AI script endpoints change a tap for](#create-or-update-tap)). A request without `tapName` changes no stored tap. Review needs only `tap:read` in this release; a later release requires `tap:update` for it, and `datris doctor` lists under `tap.references` the users and keys that used review without it.

When `rewritten` is `false`, `script` / `scriptPath` match the input and `changes` is empty — the reviewer found nothing in the output worth acting on. Prompt fragments configured via [Tap Prompt Fragments](#tap-prompt-fragments) are auto-injected into the reviewer's system prompt when their key or any alias appears in the script.

## Optimize Script

```
POST /api/v1/tap/optimize
Content-Type: application/json
```

After a successful test, asks the LLM to restructure a working script for performance — e.g. swap serial HTTP calls for a `ThreadPoolExecutor`, reuse a `requests.Session()`, or drop unnecessary `time.sleep()` — while preserving correctness (`fetch()` signature, `DATRIS_TAP_TEST_LIMIT` handling, Vault env-var reads, retry/backoff behavior, and `raise_for_status` calls).

The UI invokes this automatically after a green test in the Create Tap wizard, with a regression guard that auto-reverts if the rewrite runs ≥20% slower. Callers integrating this endpoint directly should implement the same re-test + revert pattern.

**Body:**
```json
{
  "tapName": "stock-prices-tap",
  "script": "current working script content...",
  "recordCount": 503,
  "durationMs": 298000,
  "logs": "Retrieved 503 tickers...",
  "oldScriptPath": "tap-scripts/stock-prices-tap_v3.py"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `tapName` | string | Tap identifier. Used for script path versioning. |
| `script` | string | The current working script that passed its test. |
| `recordCount` | integer | How many records the last test returned. Used in the user prompt so the LLM can reason about per-record timing. |
| `durationMs` | integer | Wall time of the last test run in ms (from `/tap/test` response). |
| `logs` | string | Recent script stderr output (last ~40 lines used). |
| `oldScriptPath` | string | MinIO path of the current script. The optimized script is stored as a new version; the old path is retained so the caller can revert. |

**Response:**
```json
{
  "script": "optimized Python 3 script...",
  "packages": ["extra-package"],
  "scriptPath": "tap-scripts/stock-prices-tap_v4.py",
  "changes": [
    "Parallelized ticker fetches with ThreadPoolExecutor(10)",
    "Removed per-item 0.25s sleep"
  ]
}
```

If the LLM concludes the script is already well-optimized, `changes` is an empty array and `script` / `scriptPath` match the input. In that case no re-test is needed.

## Run Tap

```
POST /api/v1/tap/run
Content-Type: application/json
```

Executes a saved tap. Optionally sends data to the configured pipeline.

**Body:**
```json
{
  "name": "stock-prices-tap",
  "mode": "run",
  "params": {"since": "2026-05-01"}
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `name` | string | (required) | Tap name |
| `mode` | string | `"test"` | `"run"` feeds records into `targetPipeline`; `"test"` executes the script and returns sample results without persisting. A successful `mode=test` also records `lastTestRunStatus: "success"` and `lastTestRunScriptId` (the identity of the tested script or endpoint) on the tap, which is what allows a `cronExpression` to be saved — see the test-before-cron rule under Create or Update Tap. Case-insensitive; missing or empty means `"test"`. Any other value is refused with **HTTP 400** `{"error": "Unknown mode '<mode>'. Valid values: run, test (default)."}` before the tap is read or run |
| `testLimit` | integer (optional) | `20` when `mode=test` | Max records a test pulls before the runner stops the script. Applies to `mode=test` only: the runner injects `DATRIS_TAP_TEST_LIMIT=<N>` and stops pulling from a generator `fetch()` after `N` records. `0` (or a negative value) disables the cap and streams the whole source. Ignored for `mode=run`, which always reads every row |
| `params` | object | `{}` | Optional per-run parameters exposed to the script as environment variables (nested values JSON-encoded) |

**Response:**
```json
{
  "tap": "stock-prices-tap",
  "description": "Fetch daily stock prices...",
  "status": "success",
  "mode": "run",
  "targetPipeline": "stock-prices",
  "persisted": true,
  "publisherToken": "5b2f4a1d-8c7e-4f0a-9b3d-6e1c2a4f8b9e",
  "pipelineTokens": ["a1b2c3d4-..."],
  "recordCount": 503,
  "dataType": "csv",
  "columns": ["ticker", "date", "open", "high", "low", "close", "volume"],
  "logs": "...",
  "error": null
}
```

`columns` lists the column names the script produced (normalized for `dataType: "csv"`, see [Test Tap](#test-tap)); it is `null` when the run produced no records.

**`mode=run` does not return the records themselves** — the data is in transit to `targetPipeline`, and the agent / caller should verify completion via `get_pipeline_status`, not read from the response body. `recordCount` summarizes how many records were submitted. To preview what a script produces, call the same endpoint with `mode=test`, which pulls only the first 20 records by default (raise or remove the cap with `testLimit`) and returns up to 20 sample rows in a `records` array (with `recordsTruncated: true` set when the script produced more than that). Because of the cap, a test’s `recordCount` is the preview size, not what a `mode=run` call will produce.

`persisted: true` means the records were submitted to `targetPipeline`. When `persisted: false`, a `persistedReason` field names the cause — one of `test_mode`, `run_error`, `no_records`, `no_target_pipeline`, or `debounced`. On persisted runs, `publisherToken` groups every ingestion job this run submitted; `pipelineTokens` lists each. Document taps fan out to many `pipelineTokens` but share one `publisherToken`.

### Run debounce (mode=run only)

`/tap/run` debounces `mode=run` requests per tap on a 5-second window to suppress accidental duplicates — agents that emit parallel `tool_use` blocks, UI buttons that get double-clicked, or transport-level retries. If a second run hits within the window, the response is HTTP 200 with `status: "skipped"`, `persisted: false`, `persistedReason: "debounced"`, and an `error` string explaining how long ago the previous run started. The previous run keeps executing — pivot via `get_tap_logs` and `get_pipeline_status` to track its outcome. `mode=test` is read-only and is never debounced.

### Watching a tap run

A `/tap/run` response comes back as soon as records are handed off to the async ingestion pipeline — the actual load is still in progress. Use `publisherToken` to poll:

```
GET /api/v1/pipeline/status?publishertoken={publisherToken}&withrollup=true
```

Returns a `{rollup, events}` wrapper covering every ingestion job this tap run submitted (for structured taps that's one job; for document taps it's one per submitted document). Poll until `rollup.allDone` is `true`, then read `rollup.status` for the outcome and `rollup.jobs[].lastError` for any failure. See the [Pipeline Status API → Rollup Response](/api-reference/status-api#rollup-response) for the full shape.

## Incremental-Sync State

Incremental taps save a bookmark (cursor, high-water mark, page token) after each successful run; the next run receives it in the `DATRIS_TAP_STATE` environment variable. See [Incremental Sync](/taps#incremental-sync-state) for the concept and the script-side contract; these endpoints read, overwrite and reset the stored object. Its shape is defined by the tap's own script, and committed state is capped at 64 KB.

### Read state

```
GET /api/v1/tap/state?name={tapName}
```

**Response:**
```json
{
  "tap": "stock-prices-tap",
  "state": {"cursor": "2026-04-20"},
  "updatedAt": "2026-04-20 14:05:00 UTC",
  "updatedBy": "stock-prices-tap|2026-04-20 14:05:00 UTC"
}
```

`state` is `null` (and `updatedAt` / `updatedBy` are omitted) when the tap has never committed state — a non-incremental tap, or no successful run yet. `updatedBy` is the committing run's key (`tapName|runTime`), or `manual` for an API or UI override.

### Overwrite state

```
POST /api/v1/tap/state
Content-Type: application/json
```

Sets the object the next run receives — for example, rewind a cursor so a window is re-fetched. `{}` is a valid "reset to first-run" value; to remove the state entirely use the DELETE below.

**Body:**
```json
{
  "name": "stock-prices-tap",
  "state": {"cursor": "2026-04-01"}
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `name` | string | Yes | Tap name. |
| `state` | object | Yes | Must be a JSON object. |

**Response:**
```json
{
  "tap": "stock-prices-tap",
  "state": {"cursor": "2026-04-01"},
  "message": "State saved. The next run receives it via DATRIS_TAP_STATE."
}
```

**Errors:** **HTTP 404** `{"error":"Tap: <name> not found"}`; **HTTP 500** when `name` is missing, `state` is absent, or `state` is not a JSON object.

### Reset state

```
DELETE /api/v1/tap/state?name={tapName}
```

Deletes the stored state. The next run sees no `DATRIS_TAP_STATE` and performs a full first-run fetch.

**Response:** `{"message": "State reset for tap: <name>. The next run starts from scratch (full fetch)."}`

## Tap Prompt Fragments

User-configured system prompt fragments that auto-inject into tap AI flows when the user's text matches the fragment's key or any alias. See [Tap Prompt Fragments](/tap-prompts) for the full concept; this section covers the REST endpoints.

Fragments are per install, stored in MongoDB at `{env}-tap-prompt`, and matched case-insensitively with word boundaries.

### List Fragments

```
GET /api/v1/tap-prompts
```

| Parameter | In | Description |
|---|---|---|
| `status` | query | Optional. `active` returns person-written or accepted fragments (fragments saved before statuses existed count as active); `suggested` returns fragments the recovery agent proposed from an incident. Omit for all. |

**Response:** Array of `TapPromptFragment` objects. Suggested fragments also carry `status: "suggested"`, `origin: "incident"`, and `incidentId` (the incident whose learn note produced them), and stay `enabled: false` until a person accepts them.

```json
[
  {
    "key": "AWS",
    "aliases": ["S3", "EC2", "Lambda", "boto3"],
    "content": "When fetching data from AWS services, prefer boto3 with IAM credentials...",
    "enabled": true,
    "createdAt": "2026-04-20 14:05:00 UTC",
    "updatedAt": "2026-04-20 14:05:00 UTC"
  }
]
```

### Get Fragment

```
GET /api/v1/tap-prompts/{key}
```

Returns a single fragment or HTTP 404 if `{key}` is not found. `{key}` should be URL-encoded.

### Create or Update Fragment

```
POST /api/v1/tap-prompts
Content-Type: application/json
```

Create-or-update semantics — if a fragment with the same `key` already exists, it is overwritten. `createdAt` is preserved across updates; `updatedAt` is refreshed on every write. Writing through this endpoint invalidates the in-process fragment cache immediately, so the next tap generation / fix / optimize / brainstorm call sees the change without restart.

**Body:**
```json
{
  "key": "Polygon",
  "aliases": ["polygon.io"],
  "content": "Use the requests library with os.environ.get(\"POLYGON_API_KEY\") and pass auth via the Authorization: Bearer {key} header (query param ?apiKey= also works but prefer the header).",
  "enabled": true
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `key` | string | Yes | Primary match keyword. Unique per install. Matched case-insensitively with `\b` word boundaries. |
| `aliases` | string[] | No | Additional match keywords. Same matching rules as `key`. |
| `content` | string | Yes | System-prompt text appended under a `## User-provided context` block when a match fires. |
| `enabled` | boolean | No (default `true`) | When `false`, the fragment stays in storage but is excluded from matching. |

**Response:** `{"status": "ok"}` on success.

### Delete Fragment

```
DELETE /api/v1/tap-prompts/{key}
```

Deletes the fragment and invalidates the cache. URL-encode `{key}`. Returns `{"status": "ok"}`.

### Suggest Fragment Content

```
POST /api/v1/tap-prompts/suggest
Content-Type: application/json
```

Asks the LLM to draft a content body from the fragment's key and aliases. Useful as a starting point when creating a fragment — the UI exposes this via the **Suggest** button next to the Content field. If `content` is non-empty in the request, the LLM is instructed to refine/expand it rather than replace.

**Body:**
```json
{
  "key": "Stripe",
  "aliases": ["stripe.com"],
  "content": ""
}
```

**Response:**
```json
{
  "content": "Use the stripe Python SDK (pip install stripe). Set stripe.api_key = os.environ.get(\"STRIPE_API_KEY\"). Use auto_paging_iter() for list endpoints to transparently handle pagination..."
}
```

The response is plain text — the UI drops it into the Content textarea for the user to review before saving.

## Authentication

All endpoints require the `x-api-key` header if API key authentication is enabled.
