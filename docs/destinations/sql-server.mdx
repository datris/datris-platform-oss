Use this destination when you want an agent or a scheduled pipeline to land validated data in a Microsoft SQL Server or Azure SQL database you already run, without handing the agent database credentials. Each pipeline references its own secret, and every load is audited and lineage-tracked.

The SQL Server destination works the way the [PostgreSQL destination](/destinations/postgres) does: the table is created from the destination schema on the first run, new columns are added on later runs, `keyFields` upserts with `MERGE`, `truncateBeforeWrite` replaces the rows, and the load runs in one transaction. Rows go through the driver's bulk-copy batch insert. JSON and XML sources land as a single document column, exactly as they do on PostgreSQL.

Unlike the bundled PostgreSQL and MongoDB destinations, SQL Server is an external target: credentials are per-pipeline, referenced by name through `credentialsSecret`, the same model as the [Snowflake](/destinations/snowflake) and [S3](/destinations/s3) destinations. Different pipelines can write to different servers. Datris never starts a SQL Server for you.

## One-time SQL Server setup

Give Datris its own principal with only the rights it needs: create tables in one schema and read and write the rows in them. Run the statements in the database the pipelines load into (`USE <database>;` first). The examples use the database `datris` and the default schema `dbo`.

### SQL login (`authMethod: sql`)

The server must allow SQL Server authentication (mixed mode). Azure SQL always does.

```sql
-- In master (on Azure SQL: connected to the master database)
CREATE LOGIN datris_loader WITH PASSWORD = '<strong password>';

-- In the target database
USE datris;
CREATE USER datris_loader FOR LOGIN datris_loader;
```

### Microsoft Entra service principal (`authMethod: entraServicePrincipal`)

Register an app in Microsoft Entra ID, create a client secret for it, and make the app a contained user of the database. The server must have a Microsoft Entra admin set.

```sql
-- Connected to the target database as the Microsoft Entra admin
CREATE USER [datris-loader-app] FROM EXTERNAL PROVIDER;
```

`datris-loader-app` is the app registration's display name.

### Microsoft Entra user and password (`authMethod: entraPassword`)

A Microsoft Entra user signs in with a password. The account cannot require MFA, so prefer a service principal for unattended loads.

```sql
CREATE USER [loader@example.com] FROM EXTERNAL PROVIDER;
```

### Managed identity (`authMethod: entraManagedIdentity`)

Only works when the Datris server runs on Azure (a VM, Container Apps or AKS) with a managed identity attached. No password or client secret is stored anywhere.

```sql
-- The identity's name: the VM / container app name for a system-assigned
-- identity, or the user-assigned identity's resource name
CREATE USER [datris-vm] FROM EXTERNAL PROVIDER;
```

For a user-assigned identity, put its client ID in the secret's `managedIdentityClientId`.

### Kerberos (`authMethod: kerberos`)

For an on-premises SQL Server joined to Active Directory. The server needs an SPN for `MSSQLSvc/<host>:<port>`, and the Datris principal needs a Windows login.

```sql
CREATE LOGIN [CORP\svc_datris] FROM WINDOWS;
USE datris;
CREATE USER [CORP\svc_datris] FOR LOGIN [CORP\svc_datris];
```

See [Kerberos container setup](#kerberos-container-setup) for the files the Datris container needs.

### Grants (every method)

Replace `datris_loader` with the user created above.

```sql
USE datris;
GRANT CREATE TABLE TO datris_loader;
GRANT ALTER, SELECT, INSERT, UPDATE, DELETE ON SCHEMA::dbo TO datris_loader;
-- Only if pipelines name a schema that does not exist yet:
GRANT CREATE SCHEMA TO datris_loader;
```

`ALTER` on the schema covers creating tables in it, adding columns on later runs, `TRUNCATE`, and dropping the table when a pipeline is deleted with its data. If you manage tables yourself (`manageTableManually: true`), `SELECT, INSERT, UPDATE, DELETE` on those tables is enough.

## Create the platform secret in Datris

On **Configuration → Secrets → Platform**, create a secret (for example `sqlserver`). `host` is always required; `authMethod` selects the other fields.

| Field                     | Used by                                 | Notes |
|---------------------------|-----------------------------------------|-------|
| `host`                    | every method                            | Server name, e.g. `sql01.example.com` or `myserver.database.windows.net` |
| `port`                    | every method (optional)                 | Default `1433` |
| `authMethod`              | every method (optional)                 | `sql` (default), `entraServicePrincipal`, `entraPassword`, `entraManagedIdentity` or `kerberos` |
| `user`, `password`        | `sql`, `entraPassword`                  | The SQL login, or the Microsoft Entra user (`loader@example.com`) |
| `clientId`, `clientSecret`, `tenantId` | `entraServicePrincipal`    | From the app registration |
| `managedIdentityClientId` | `entraManagedIdentity` (optional)       | Only for a user-assigned identity |
| `principal`, `password`   | `kerberos`                              | e.g. `svc_datris@CORP.EXAMPLE.COM` |
| `jaasConfigurationName`   | `kerberos` (optional)                   | Entry in a mounted JAAS file, for a keytab instead of a password |
| `encrypt`                 | every method (optional)                 | Default `true` |
| `trustServerCertificate`  | every method (optional)                 | Default `false`. Set `true` only for a test server with a self-signed certificate |

The database name is not in the secret: each pipeline names it in `dbName`, so one secret can serve several databases on the same server. If a required field is missing, the load fails with an error naming the secret, the field and the auth method. A secret with any complete auth method makes SQL Server appear in the pipeline wizard and in the Assistant's destination question.

The installer can create this secret for you: answer yes to "SQL Server destination — configure credentials now?", or for a headless install export `SQLSERVER_HOST`, `SQLSERVER_AUTH_METHOD` and that method's fields (`SQLSERVER_USER`, `SQLSERVER_PASSWORD`, `SQLSERVER_CLIENT_ID`, `SQLSERVER_CLIENT_SECRET`, `SQLSERVER_TENANT_ID`, `SQLSERVER_PRINCIPAL`, `SQLSERVER_MANAGED_IDENTITY_CLIENT_ID`) before running it. The secret is seeded once, as `sqlserver`, and never overwritten afterwards.

## Kerberos container setup

The Datris server runs on Linux, so Kerberos uses the JDK's own Kerberos client, not Windows integrated security.

1. Put your `krb5.conf` in `docker/config/`. The compose file mounts that folder at `/config` in the `datris` container.
2. Add the JVM flag in `.env`, keeping your heap settings:
   ```bash
   JAVA_OPTS=-Xms512m -Xmx2g -Djava.security.krb5.conf=/config/krb5.conf
   ```
3. With `principal` and `password` in the secret nothing else is needed. To use a keytab instead, put the keytab and a JAAS file in `docker/config/`, add `-Djava.security.auth.login.config=/config/jaas.conf` to `JAVA_OPTS`, and set the secret's `jaasConfigurationName` to the entry name:
   ```
   DatrisKeytab {
     com.sun.security.auth.module.Krb5LoginModule required
       useKeyTab=true keyTab="/config/datris.keytab"
       principal="svc_datris@CORP.EXAMPLE.COM" doNotPrompt=true;
   };
   ```
4. Recreate the container: `docker compose up -d datris`.

The standalone compose file has no `docker/config` bind mount; add one to the `datris` service to use Kerberos there.

## Configuration

A CSV source:

```json
{
  "name": "orders_pipeline",
  "source": { "..." : "..." },
  "destination": {
    "database": {
      "useSqlServer": true,
      "credentialsSecret": "sqlserver",
      "dbName": "datris",
      "schema": "dbo",
      "table": "orders",
      "keyFields": ["order_id"]
    }
  }
}
```

A JSON source. The schema is the single `_json` field, and every document lands whole in it:

```json
{
  "name": "events_pipeline",
  "source": {
    "fileAttributes": { "jsonAttributes": {} },
    "schemaProperties": { "fields": [{ "name": "_json", "type": "string" }] }
  },
  "destination": {
    "database": {
      "useSqlServer": true,
      "credentialsSecret": "sqlserver",
      "dbName": "datris",
      "schema": "dbo",
      "table": "events"
    }
  }
}
```

An XML source is the same with `xmlAttributes` and a single `_xml` field.

### Field reference

| Field                 | Required | Default | Description |
|-----------------------|----------|---------|-------------|
| `useSqlServer`        | yes      | `false` | Must be `true` to enable the SQL Server destination |
| `credentialsSecret`   | yes      |         | Name of the Platform secret holding `host` and the auth fields |
| `dbName`              | yes      |         | Target database on the server |
| `schema`              | yes      | `dbo`   | Target schema (the wizard and MCP server fill in `dbo`) |
| `table`               | yes      |         | Target table |
| `manageTableManually` | no       | `false` | If `true`, skip creating the schema and table and adding columns |
| `truncateBeforeWrite` | no       | `false` | Empty the table before loading (see below) |
| `keyFields`           | no       |         | Natural-key columns; switches the load to a `MERGE` upsert |
| `useTransaction`      | no       | `true`  | Run the load in one transaction |

Simple identifiers (letters, digits, underscores) are passed unquoted and resolve the way SQL Server always does (case-insensitive under the default collation). Other names are bracket-quoted, for example `[order details]`.

## Table management

When `manageTableManually` is `false` (the default), the pipeline creates the schema if it is missing and the table if it is missing (checked through `sys.tables`), with a `PRIMARY KEY` on `keyFields` when set. Schema changes are additive: new columns in the pipeline schema are added with `ALTER TABLE ... ADD`; columns are never dropped or retyped.

## Type mapping

| Source type                              | SQL Server type |
|------------------------------------------|-----------------|
| `string`                                 | `NVARCHAR(MAX)` (`NVARCHAR(450)` for a key column) |
| `int` / `integer` / `smallint` / `tinyint` | `INT`         |
| `bigint`                                 | `BIGINT`        |
| `float` / `double`                       | `FLOAT`         |
| `boolean`                                | `BIT`           |
| `date`                                   | `DATE`          |
| `timestamp`                              | `DATETIME2`     |
| `_json`                                  | `NVARCHAR(MAX)` with `CHECK (ISJSON(_json) = 1)` |
| `_xml`                                   | `XML`           |

Other types (`decimal(p,s)`, `varchar(n)`) pass through as-is. A string key column is `NVARCHAR(450)` because SQL Server cannot index an `NVARCHAR(MAX)` column. A JSON document that is not valid JSON fails the load on the `ISJSON` check. An XML document's `<?xml ...?>` declaration is dropped before the insert, because the `XML` type does not keep it.

## Truncate before write

Set `truncateBeforeWrite` to `true` to replace the full table contents on each run:

- **`useTransaction: true` (default):** rows are removed with `DELETE FROM` inside the load transaction. If the load fails, the delete rolls back and the previous rows survive.
- **`useTransaction: false`:** rows are removed with `TRUNCATE TABLE`, which is faster on large tables; a failure after it leaves the table empty until the next successful run.

## Primary key and upsert

Specify one or more columns in `keyFields` to define the natural key. When set (and `truncateBeforeWrite` is `false`), the loader inserts the batch into a session temp table (`#DATRIS_STG_<id>`) and runs a `MERGE` on the key columns: matched rows are updated, unmatched rows are inserted. The same rows can be loaded across runs without duplicates.

Upsert semantics match the PostgreSQL destination: on match, non-key columns are overwritten in full, including `NULL`s. If one batch holds the same key twice, SQL Server rejects the `MERGE`; deduplicate upstream.

When `keyFields` is empty, rows are inserted straight into the table.

## Deleting a pipeline

Deleting a pipeline with its data drops the table (`DROP TABLE IF EXISTS`), connecting with the pipeline's own credentials secret.

## Errors

Connection failures name the auth method and the fix: a rejected login points at the secret's fields for that method, `Cannot open database` at the database name and the user mapping, an unreachable host at `host`, `port` and the firewall, and a Kerberos failure at `krb5.conf` and `JAVA_OPTS`. The run status names `SqlServerLoader` as the failing step.

## Manual checks before relying on Entra ID or Kerberos

The unit tests cover how each auth method's connection settings are built. A real sign-in needs a real directory, so check these once by hand:

- **Service principal:** create the secret with `authMethod: entraServicePrincipal` against an Azure SQL database, run a small CSV pipeline, and confirm the rows land.
- **Managed identity:** run Datris on an Azure VM or container with the identity attached, create a secret with only `host` and `authMethod: entraManagedIdentity`, and run the same pipeline.
- **Kerberos:** against a domain-joined SQL Server, with `krb5.conf` mounted and `JAVA_OPTS` set as above, run the pipeline with `principal` and `password` in the secret.
