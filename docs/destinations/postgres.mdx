Use this destination when an agent, a tap, or a scheduled pipeline needs to land rows in PostgreSQL and you want the write validated against a schema, recorded in the audit log, and traceable to the run that produced it.

The PostgreSQL destination performs bulk inserts using the PostgreSQL `COPY` command. It streams data directly into the target table, making it significantly faster than row-by-row inserts.

## Connection

Connection credentials are retrieved from Vault using the secret name specified in `secrets.postgresSecretName` in `application.yaml`. The secret must contain the following keys:

| Key        | Description                              |
|------------|------------------------------------------|
| `jdbcUrl`  | JDBC connection string for the database  |
| `username` | Database user                            |
| `password` | Database password                        |
| `queryUsername` | Optional. A separate login for read-back queries; see [Separate query login](#separate-query-login) |
| `queryPassword` | Optional. That login's password |

`username` and `password` are the loading login: loads, deletes, schema migrations, the PostgreSQL listings in the Data tab and the health check use it. As for any service account, give it only the privileges it needs (create and write in the destination schemas) rather than a superuser. The read-back queries (`query_postgres`, `query_natural` and `POST /api/v1/query/postgres`) run in read-only transactions and use the same login unless the secret names a separate query login.

## Separate query login

The read-only transaction stops a query from writing, but it does not narrow what the login can read: with the bundled `postgres` superuser, a query can read other databases on the same server, the system catalogs and server settings. To put a second limit behind it, give Datris a second PostgreSQL user that can only read what you grant it. Read-back queries then connect as that user while loads keep the loading login.

Datris does not create the user or grant anything; you run the SQL below as an administrator. In it, replace `datris_reader` and `<password>` with the query user and its password, `<loading login>` with the `username` in the secret, `datris` with a database the pipelines load into, and `public` with a schema they load into.

### Recommended: grant reads on the Datris schemas only

**Once per server.** A role belongs to the whole server, so create it once:

```sql
CREATE ROLE datris_reader LOGIN PASSWORD '<password>' NOSUPERUSER NOCREATEDB NOCREATEROLE;
```

**Once per database** the pipelines load into (the default is `datris`; pipelines can name others with `dbName`). Connect to that database first, since grants and default privileges apply only to the database you are connected to:

```sql
GRANT CONNECT ON DATABASE datris TO datris_reader;

-- Each schema that already holds pipeline tables:
GRANT USAGE ON SCHEMA public TO datris_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO datris_reader;

-- Tables and schemas the loading login creates from now on, in any schema of this database:
ALTER DEFAULT PRIVILEGES FOR ROLE <loading login> GRANT SELECT ON TABLES TO datris_reader;
ALTER DEFAULT PRIVILEGES FOR ROLE <loading login> GRANT USAGE ON SCHEMAS TO datris_reader;
```

The last two lines matter because loads create tables, and create the schema too when a pipeline names one that does not exist yet. Default privileges cover only objects that `<loading login>` creates, in the database you ran them in, after you ran them. A database created later (a new `dbName`) has no grants at all until you run the per-database block in it. Tables created before the grants, or by another role, need their own `GRANT SELECT`.

### Convenient but broad: `pg_read_all_data`

On PostgreSQL 14 and later, one built-in role replaces the per-schema grants:

```sql
CREATE ROLE datris_reader LOGIN PASSWORD '<password>' NOSUPERUSER NOCREATEDB NOCREATEROLE;
GRANT pg_read_all_data TO datris_reader;
```

This role can read every table, view and sequence in every database it can connect to, including tables that are not Datris's and tables created later. By default every role may connect to every database, so this leaves the opening problem, reading other databases on the same server, largely open. If you use it, stop it connecting elsewhere with `REVOKE CONNECT ON DATABASE <other database> FROM PUBLIC;` for each database it should not reach, then grant `CONNECT` back to the roles that need it. Prefer the recommended form above.

### Add the login to the secret

Add two keys to the platform Postgres secret: **Configuration → Secrets → Platform**, select `postgres`, **Edit**, use **Add Field** to add `queryUsername` with the query user's name and `queryPassword` with its password, then **Save**. Values are used exactly as written, so type them without surrounding spaces. The secret is read on every query, so the next query uses the new login; no restart is needed.

A direct Vault write works too. Use `patch`, which adds to the secret (`vault kv patch secret/oss/postgres queryUsername=datris_reader queryPassword=<password>`, run in the vault container as shown in [Setting Secrets Manually](/ai-configuration#setting-secrets-manually)). The bundled stack seeds the secret only when it is missing, so a restart keeps the keys.

**Keeping and removing the keys.** The Secrets editor keeps both keys on later edits: it shows `queryPassword` masked and sends it back unchanged unless you type a new one, and an empty password box also keeps the stored value. To stop using the query login, **Clear** both fields and save. A save replaces the whole secret, so any writer that sends only `jdbcUrl`, `username` and `password` (an API client calling `PUT /api/v1/secrets/postgres`, or `vault kv put` in place of `patch`) removes both keys without a warning, and queries go back to the loading login. The server logs one info line at the next query when that happens. Removing only one of the two keys does not do this: queries are then refused (see below).

### What uses which login

| Uses the query login | Keeps the loading login |
|---|---|
| `query_postgres`, `query_natural`, `POST /api/v1/query/postgres`, `POST /api/v1/query/natural` and its column lookup, tap scripts reading platform data through the query API, the landed-row sample behind a destination-type proposal, and the landed-row profile in incident evidence | Loads, truncates and upserts, table drops on pipeline delete, destination-type migrations, the PostgreSQL database, schema, table and column listings (`list_postgres_*`, the Data tab and the metadata API), the health check and destination availability probe |

### What callers see

- **Both keys or neither.** A secret with `queryUsername` but no `queryPassword`, or the reverse, refuses every query with a message naming the missing key; queries never fall back to the loading login. An empty or blank value counts as not set. Loads are not affected.
- **A different user.** `queryUsername` must name a different PostgreSQL user from `username`. The same user with a different password is refused on every query in the same way. The same user with the same password is simply the loading login.
- **Statuses.** A refused login answers `500` with `{"error": "<message>"}` on `POST /api/v1/query/postgres` and `POST /api/v1/query/natural` (and the MCP tools show the message), and `400` on a destination-type proposal.
- **A table the query user cannot read.** The query routes answer `500` with PostgreSQL's `permission denied` message. A destination-type proposal answers `400` saying the login Datris uses for queries has no permission to read the table. Incident evidence quietly falls back to the column names of the tap's last run instead of profiling landed rows.
- **`SELECT current_user`** through `POST /api/v1/query/postgres` returns the user queries run as.

### Check it with doctor

With the keys set, the `postgres.query_login` [doctor](/doctor) check connects as the query login and warns when it is a superuser, cannot connect, or the keys are incomplete or name the loading user. It connects to the default database (`postgres.database`, normally `datris`) only, so a login granted `CONNECT` on other pipeline databases but not on the default one shows as unable to connect.

## Table Management

When `manageTableManually` is set to `false` (the default), the pipeline auto-creates the target table if it does not exist. The table schema is derived from the pipeline's destination schema if one is defined, otherwise it falls back to the source schema. Types are mapped using the table below.

Set `manageTableManually` to `true` if you want to create and manage the table yourself. In this case the table must already exist and its column types must be compatible with the incoming data.

## Type Mapping

When auto-creating tables, source schema types are mapped to PostgreSQL types as follows:

| Source Type | PostgreSQL Type |
|-------------|-----------------|
| `tinyint`   | `int2`          |
| `smallint`  | `int2`          |
| `float`     | `float4`        |
| `double`    | `float8`        |
| `string`    | `text`          |
| field named `_json` \* | `json`  |
| field named `_xml` \*  | `xml`   |

\* Matched on the field **name**, not its declared type: a field named `_json` or `_xml` (declared `string`, as the JSON and XML ingestion modes produce) always lands as the document column shown, whatever type it declares.

All other types (`int`, `bigint`, `boolean`, `date`, `timestamp`, `decimal(p,s)`, `varchar(n)`, `char(n)`) are passed to PostgreSQL as written. A `tinyint` or `double` column added to an existing table (schema evolution) is created as `int2` or `float8`, as in the table above. A stored type that is not one of the accepted forms (see [Schemas](/schemas)) is never sent: while the table and that column already exist the load continues and the run notes the field; when the table or the column would have to be created, the run fails before any statement with a message naming the field. A stored type with tabs or line breaks around the numbers or after the closing parenthesis is sent with them removed. Change the type to an accepted form and save the pipeline.

## Truncate Before Write

Set `truncateBeforeWrite` to `true` to issue a `TRUNCATE` statement on the target table before loading data. This replaces the full contents of the table on each run.

## Transaction Support

All writes are wrapped in a database transaction by default (`useTransaction: true`). If any error occurs during the `COPY` operation, the transaction is rolled back and no partial data is committed. Set `useTransaction` to `false` to disable transactional writes.

## Primary Key and Upsert

Specify one or more columns in `keyFields` to define the natural key for the target table. `keyFields` controls **two** behaviors:

1. **Table shape.** When `manageTableManually` is `false`, the auto-created table includes a `PRIMARY KEY` constraint on these columns.
2. **Load strategy.** When `keyFields` is set and `truncateBeforeWrite` is `false`, the loader switches from raw `COPY` to an upsert path: `COPY` into a session-local staging table, then `INSERT ... SELECT ... ON CONFLICT (keyFields) DO UPDATE SET <non_key_cols> = EXCLUDED.<non_key_cols>` into the target. Rows that match an existing primary-key tuple replace the existing row; rows that don't match are inserted. The same row can therefore be loaded across multiple runs without violating the unique constraint.

**Retrofitting `keyFields` onto an existing table:** if you add `keyFields` to a pipeline that's been loading without it, the underlying table may not have a matching unique constraint yet. The loader auto-creates a unique index on the keyFields columns the next time it runs. If the existing data already contains rows that violate the proposed uniqueness, the index creation fails with a clear remediation message — deduplicate the existing rows, or set `truncateBeforeWrite: true` to wipe and reload from scratch.

**Upsert semantics — on conflict, non-key columns are overwritten in full, including NULLs.** This matches MongoDB's `keyFields` behavior (true upsert, not a non-null merge). Sources that emit partial rows and don't want NULLs to clobber existing values should coalesce upstream before the pipeline.

**When `keyFields` is empty,** the loader uses raw `COPY` directly into the target table. This is the fastest path; duplicate-key violations against any pre-existing unique constraint fail the load. Use this for append-only ingestion where duplicates aren't expected.

**When `truncateBeforeWrite: true`,** the loader uses raw `COPY` regardless of `keyFields` because truncate already prevents duplicates. The upsert path would just be slower with no benefit.

## Schema Auto-Creation

When `manageTableManually` is `false`, the pipeline also creates the target schema if it doesn't exist (`CREATE SCHEMA IF NOT EXISTS`).

## Custom COPY Options

Use the `options` array to pass additional PostgreSQL `COPY` options. Each entry is appended to the `COPY` command. When no options are specified, the default is `FORMAT csv` — Postgres CSV mode treats unquoted empty fields as `NULL` automatically. If your source uses a non-empty placeholder for missing values (e.g. a literal `.`), normalize it at the source layer or set the `NULL` option explicitly via `options`.

## Configuration Example

```json
{
  "name": "orders_pipeline",
  "source": { "..." : "..." },
  "destination": {
    "database": {
      "dbName": "analytics",
      "schema": "public",
      "table": "orders",
      "usePostgres": true,
      "manageTableManually": false,
      "truncateBeforeWrite": true,
      "keyFields": ["order_id"],
      "options": ["NULL 'NA'"]
    }
  }
}
```

Connection credentials are configured globally in `application.yaml` via `secrets.postgresSecretName`, not per pipeline. See [Configuration Reference](/configuration-reference) for Vault secret format.

### Field Reference

| Field                 | Required | Default  | Description                                      |
|-----------------------|----------|----------|--------------------------------------------------|
| `dbName`              | yes      |          | Target database name. Letters, digits and `_` only, at most 63 bytes. Ignored when the platform Postgres connection URL already names a database (the table is then created there) |
| `schema`              | yes      |          | Target schema. The literal placeholder `SCHEMA_NAME` is replaced with `public` when the pipeline is saved (likewise `DATABASE_NAME` in `dbName` becomes the configured Postgres database); any other value is used as-is. Letters, digits and `_` only, at most 63 bytes |
| `table`               | yes      |          | Target table name. Letters, digits and `_` only, at most 63 bytes |
| `usePostgres`         | yes      | `false`  | Must be `true` to enable PostgreSQL destination  |
| `manageTableManually` | no       | `false`  | If `true`, skip auto-creation of the table       |
| `truncateBeforeWrite` | no       | `false`  | Truncate the table before loading                |
| `keyFields`           | no       |          | Array of column names for the natural key. Sets a `PRIMARY KEY` constraint on auto-created tables AND switches the load strategy to upsert (`INSERT ... ON CONFLICT DO UPDATE`) when `truncateBeforeWrite` is `false`. See [Primary Key and Upsert](#primary-key-and-upsert). |
| `useTransaction`      | no       | `true`   | Wrap the COPY in a database transaction          |
| `options`             | no       |          | Array of additional COPY option strings (no `;`) |

These rules apply to every pipeline type, including an unstructured pipeline that carries a `destination.database` section, and to version restore and catalog restore. A save that keeps exactly the names the saved pipeline already has is not refused by them. Deleting a pipeline (or resetting its data) drops its table only when its database, schema and table names meet them; otherwise the table is kept and the delete response's `warnings` says so ([Delete a Pipeline](/api-reference/pipeline-api#delete-a-pipeline)).

## Querying from Datris

The Assistant (and any MCP client) can read a PostgreSQL destination back without leaving Datris. Queries run on a read-only connection, so statements that write are rejected by PostgreSQL, and a `LIMIT` is appended when the query has none (unless `limit` is `-1`).

| Tool | Purpose |
|------|---------|
| `query_postgres` | Run a `SELECT` (`sql`, optional `limit`, default 100; `-1` returns every row) |
| `list_postgres_databases`, `list_postgres_schemas`, `list_postgres_tables`, `list_postgres_columns` | Discover databases, schemas, tables and columns before writing a query |

Queries connect with the loading login, or with a separate query login when the secret names one ([Separate query login](#separate-query-login)); the `list_postgres_*` tools always use the loading login. The REST endpoint is `POST /api/v1/query/postgres` ([Query API](/api-reference/query-api#query-postgresql)); a key needs the `query:postgres` capability (included in the `read-only` and `reporting` templates). The CLI equivalent is `datris query "SELECT ..." --limit 100`.

```bash
curl -X POST http://localhost:8080/api/v1/query/postgres \
  -H "x-api-key: $DATRIS_API_KEY" -H "Content-Type: application/json" \
  -d '{"sql": "SELECT * FROM public.customers", "limit": 10}'
```
