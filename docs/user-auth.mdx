---
title: "User Authentication"
description: "Enable username/password login, admin gating, and per-user roles for the Datris UI."
---

By default, the Datris OSS install runs single-tenant with no login screen — anyone who reaches the UI URL has full access. For shared installs (a team running Datris on a server, a managed deployment, anything past your laptop), turn on user authentication so the UI requires a login and the Configuration tab is admin-only.

## What it does

When `USE_USER_AUTH=true`:

- The UI shows a **login screen** before any tab is reachable.
- Sensitive **Configuration** sub-tabs (Secrets, API-Keys, [Audit Log](/audit-log), [Agent Policy](/agent-policy)) are gated to **admin** users. The AI Providers, Data Sources, and Code Repository sub-tabs remain visible to all roles. The Users and API-Keys sub-tabs appear based on the active flags (see the [matrix](/api-keys#supported-configurations) for full visibility rules).
- A new **Users** sub-tab appears under Configuration for adding, removing, and changing roles (admin-only by virtue of being inside Configuration).
- Sessions are server-side, with a TTL index cleaning them up automatically.

When the flag is off, the toggle has zero effect on data — pipelines, taps, secrets, and run history all work the same.

## Enabling it

1. Read and save the seed account's bootstrap password. The server generates it at random when it seeds `admin` (on the first boot, whether or not `USE_USER_AUTH` is on) and prints it once, in the log of that container only. Recreating the container (step 3) discards that log, so read it first:

   ```bash
   docker compose logs datris | grep "Bootstrap login"
   ```

   If nothing is printed, the container has been upgraded or recreated since `admin` was seeded and the line is gone; see [Recovering admin access](#recovering-admin-access). If you already set your own `admin` password, use that.

2. Add the flag to your `.env`:

   ```bash
   USE_USER_AUTH=true
   ```

3. Recreate the Datris container:

   ```bash
   docker compose up -d --force-recreate datris
   ```

4. Open the UI. You'll see the login screen.

5. Log in as `admin` with the password from step 1, then change it right away (your username in the top-right → **Change password**, minimum 5 characters). After that, `admin` is your administrator account.

<Tip>
A new install can switch on login, API keys, the audit log and the agent policy in one step: run the installer with `DATRIS_GOVERNED=1`. See [Switch on the governance controls](/quick-start#2-switch-on-the-governance-controls).
</Tip>

<Note>
The default `admin` row is seeded on **every startup** (idempotent — only when the user table is empty), regardless of whether `USE_USER_AUTH` is on, with a fresh bootstrap password printed once to that container's log. The line does not survive an upgrade or a recreate of the container, so save it when you first install. That means flipping the flag on later "just works" — there's no separate provisioning step.
</Note>

## Roles

| Role | Can read pipelines / data | Can edit pipelines / taps / secrets | Can manage users + Configuration |
|---|:-:|:-:|:-:|
| **admin** | ✓ | ✓ | ✓ |
| **editor** | ✓ | ✓ |   |
| **viewer** | ✓ |   |   |

All roles see the **Configuration** tab in the top nav, but the sub-tabs differ: admins see Secrets, API-Keys, Audit Log, and Agent Policy; editors and viewers see only AI Providers, Data Sources, Code Repository, and Users. Everything outside Configuration (Pipelines, Taps, Search, etc.) is accessible to all roles per the read/write rules above.

## Adding users

As an admin: **Configuration → Users → Add user**. Fill in username + role and an initial password (type one, or click the generate button for a strong random one). Send the user their username and password out-of-band, and ask them to change it after their first login. Through the API, a `POST /api/v1/auth/users` body that omits `password` generates a random temporary password and returns it once as `temporaryPassword`.

You can change a user's role or delete them from the same screen. Datris won't let you remove the **last admin** — there's an `adminCount` guard on delete and role-change.

## Changing your own password

Click your username in the top-right → **Change password**. Enter your current password and the new one (min 5 chars).

If you've forgotten your password and there's another admin: have them delete and re-add your user with a new initial password and send it to you; log in with it and change it.

If you're the **only** admin and you've lost the password, see [Recovering admin access](#recovering-admin-access).

## Recovering admin access

Use this when you are the only admin and cannot log in: you lost the password, or the `admin` bootstrap password is no longer in the server log (it is printed once, and an upgrade or recreate of the container discards it).

At startup the server gives every account that has no password a new random bootstrap password and prints it once. So clear the account's password in MongoDB, then recreate the server. With the bundled MongoDB and the default environment `oss`, users live in the `oss-user` collection of the `oss` database (the server's internal database):

```bash
docker compose exec mongodb mongosh oss --quiet \
  --eval 'db.getCollection("oss-user").updateOne({username: "admin"}, {$set: {passwordHash: null}})'
docker compose up -d --force-recreate datris
docker compose logs datris | grep "Assigned a bootstrap password"
```

The last line prints `User 'admin' had no password set ... Assigned a bootstrap password: <password>`. Log in as `admin` with it and change it right away. Other users are untouched. Until you recreate the server, the cleared account cannot log in at all.

With the [audit log](/audit-log) on, the rotation is also recorded as `user` / `rotate-password` on the account, with the `system` actor and the time, just before that boot's `system` / `start` entry. The password itself is never in the audit log: it was printed to the log of the server container that started at that time, so if you find a `rotate-password` row you did not expect, that container's log is where the password went. An admin clearing a password from **Configuration → Users** is recorded separately as `user` / `reset-password`, with the admin as the actor.

## Reverting

Set `USE_USER_AUTH=false` (or remove the line) and recreate the Datris container. The login screen disappears; the Configuration tab is unrestricted again. **User rows persist in the database** — they just aren't checked. Flipping back on later returns you to the same set of users with the same passwords.

## Production checklist

- Run Datris **behind HTTPS** before turning auth on. Sessions are cookie-based; without TLS, the login is exposed in transit.
- Review your CORS allow-list (`cors.allowedOrigins` in `application.yaml`) — the default `"*"` is for local dev only.
- Pair this with `USE_API_KEYS=true` for any shared install — user auth gates the **UI**, API-key gating handles programmatic clients (CLI, MCP, external scripts). API keys are meant to be used **alongside** user auth: enable the two together. Turning on `USE_API_KEYS=true` without `USE_USER_AUTH=true` leaves the browser with no coherent auth mechanism — see [supported configurations](/api-keys#supported-configurations); the two are designed to compose.
