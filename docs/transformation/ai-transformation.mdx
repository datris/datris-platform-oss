AI transformations apply natural language instructions to transform data. Describe the transformation in plain English — Datris generates a Python script from your instruction and runs it against all data in an isolated runner container.
## Configuration

Add an `aiTransformation` block to the `transformation` section:

```json
"transformation": {
    "aiTransformation": {
        "instruction": "convert all date values from YYYY-MM-DD format to MM/DD/YYYY format"
    }
}
```

| Field | Type | Description |
|---|---|---|
| `instruction` | string | A natural language description of the transformation to apply to every row. |

## Examples

**Date format conversion:**
```json
"aiTransformation": {
    "instruction": "convert all date values from YYYY-MM-DD format to MM/DD/YYYY format"
}
```

**Phone number standardization:**
```json
"aiTransformation": {
    "instruction": "standardize the phone_number column to +1-XXX-XXX-XXXX format"
}
```

**Data enrichment / categorization:**
```json
"aiTransformation": {
    "instruction": "add a 'sector' column at the end based on the stock symbol, categorizing each as one of: Technology, Healthcare, Finance, Energy, Consumer, Industrial, Other"
}
```

**Combined operations:**
```json
"aiTransformation": {
    "instruction": "convert dates to YYYY/MM/DD. Trim leading/trailing whitespace from all columns. Remove duplicate rows."
}
```

## How it works

1. When the pipeline is saved, Datris combines the source schema (delimiter, column names and types) with your instruction and sends a single prompt to the AI model. When a run has to generate the script instead (see [When the script is generated](#when-the-script-is-generated)), it uses the column names and sample rows from that run's data.
2. The AI generates a self-contained Python 3 script (stdlib only) that reads the input file, applies the transformation, and writes the output. The script is stored.
3. Every run executes the stored script locally via `python3`. Runs make no model call.
4. The transformed data replaces the original and continues through the pipeline to destinations.

AI transformations run after data quality checks and before data is written to destinations.

On a compose install the script runs in `datris-codegen-runner`, an isolated container with no platform secrets, no access to the server's files, and no route to the internal services or the internet. The server sends it the script and the input file and streams the output file back. If the runner is stopped or unreachable the transformation fails with an error naming it; it never falls back to running the script in the server. See [Generated data-quality and transformation scripts](/tap-execution-isolation#generated-data-quality-and-transformation-scripts).

An `aiTransformation` whose `instruction` is empty or only whitespace is ignored: no script is generated at save and the run skips the stage with a status line saying so.

## Columns the transformation adds, removes or reorders

A transformation on delimited data can change the columns, for example "add a `sector` column". The destination schema is built from the source columns when the pipeline is saved, so it does not list a column the transformation creates. The run handles this:

- **Added columns** join the destination schema at the end, on the first run that produces them, and the stored pipeline is updated once the run has loaded them. Each is added as `string`, the same rule a [new source column](/schemas) follows, so no later run's values can fail the load because of the type. The run status lists them: "CodeGen transformation added columns to the destination schema: ...". The destination table gains the column the same way it does for a new source column. To choose the type yourself, declare the column in the destination schema before the first run; a declared column keeps its type.
- **Source columns the destination schema leaves out** stay out. A column the rows held before the transformation, or that the source schema lists, is never added, even when the transformation keeps it or changes only its letter case or surrounding spaces. On an object store, while the rows still hold such a column, no column is added and the rows load as they did before.
- **Removed columns** stay in the destination schema and are loaded as null, except on an object store when the removed column is an Iceberg `merge` key (`keyFields`) or a `partitionBy` column: the run then fails before anything is written to the object store, with a message naming the column.
- **Reordered columns** land under their own names on PostgreSQL, Snowflake, Databricks, SQL Server and the object store (Parquet, ORC, Iceberg).

An added column whose name the destination cannot hold (blank, a control character, longer than the destination allows, or a backtick on ORC), or two added columns with one name (letter case and surrounding spaces ignored), is handled by destination:

- **Without an object store destination**, the column is left out of the destination schema and the run continues, so PostgreSQL, Snowflake, Databricks and SQL Server do not load it. The run status shows a warning naming the column and the reason; the other columns load as usual, each value in its own column.
- **With an object store destination** (Parquet, ORC, Iceberg, alone or together with a database), the run fails before anything is written, with a message naming the column.

Change the instruction so each new column has a name the destination can hold.

A PostgreSQL, Snowflake, Databricks or SQL Server table may be unable to take an added column: the database refuses to add it to the table (for example when the table belongs to another user), the table is managed manually (`manageTableManually`) and does not have it, or the table already has a column of that name whose type does not take every text value. The run still succeeds: the column is left out of that table for that run, the run status shows a warning naming the column, the table and the database's reason, and every other column loads as usual, each value in its own column. Other destinations of the pipeline still receive the column. The stored destination schema gains an added column only after a run in which every database table took it, so until then each run tries again and shows the warning again. A column you declare in the destination schema yourself is not affected: if the database refuses to add it, the run fails as before.

Kafka, ActiveMQ, REST endpoint and Live Read destinations send each row under the transformation's own column names.

## When the script is generated

The script is generated once and stored, not on every run:

- **At save** — Saving a pipeline with an AI transformation (`POST /api/v1/pipeline`, the MCP `create_pipeline` tool, or the UI wizard) generates the script from the source schema: the delimiter and the ordered field names and types. No sample rows are available when a pipeline is saved, so state any format the transformation depends on in the instruction (for example "dates are YYYY-MM-DD"). The script is stored in the built-in object store under `pipeline-scripts/<pipeline>/`, or committed to the code repository when one is enabled (see [Pipeline scripts](/tap-github-storage#pipeline-scripts)).
- **Every run** — Each run executes the stored script. A run makes no model call, gives the same result for the same data, and keeps working if the model is unreachable. The status shows "Running stored CodeGen script generated at ...".
- **Re-saving** — Saving again regenerates only when the instruction or the source schema (delimiter, field names, types or order) changed. Re-saving an unchanged pipeline makes no model call. A changed CodeGen model does not regenerate: the script keeps the model that wrote it.
- **Pending** — If the script cannot be generated at save (no AI key, model unreachable, AI disabled), the pipeline is still saved, the save response carries a warning and `codegenScripts` lists the script as `pending` with the reason. JSON and XML pipelines have no column schema to generate from, so they are always saved pending. The first run generates the script from its data, stores it, and later runs reuse it.
- **Header differs** — If the header that reaches the transformation differs from the one the script was written for (for example a column was removed by field protection or is missing from the file), that run generates a script for itself only and keeps the stored one. The status says why.
- **Failures** — A stored script that exits with an error or times out fails the run. It is not regenerated automatically: the error names when the script was generated and the regenerate endpoint.

To read the stored script, call `GET /api/v1/pipelines/{name}/codegen-scripts`. To replace it (for example to adopt a new CodeGen model, or after a wrong script), call `POST /api/v1/pipelines/{name}/codegen-scripts/transformation/regenerate`, which needs the `pipeline:update` capability. If generation fails there, the current script stays in place.

Every change to the script (generated at save or at a run, regenerated, adopted from the code repository, imported by a catalog restore, or restored) is kept as a numbered version with its text. List them with `GET /api/v1/pipelines/{name}/codegen-scripts/transformation/versions`, compare two with `.../versions/{version}/diff?against={other}`, and go back to one with `POST .../versions/{version}/restore` (needs `pipeline:update`): the chosen text becomes a new latest version, with no model call, and the pipeline's definition version does not change. A restore is refused when the version was written for a different instruction or source schema than the pipeline has now. In the UI, open a run of the pipeline and choose **Script history**.

With a code repository configured under **Configuration > Code Repository**, the script for a new pipeline is committed to it as `<pathPrefix>pipelines/<pipeline>/transformation.py` and every run executes the recorded commit. You can review it, blame it and edit it in the repository; an edit is used only after you adopt it with `POST /api/v1/pipelines/{name}/codegen-scripts/transformation/pull`. See [Pipeline scripts](/tap-github-storage#pipeline-scripts) for commit messages, conflicts, and what happens when the repository is unreachable.

The **Columns** section of the [lineage panel](/provenance#column-level-lineage) shows when and by which model the stored transformation script was generated, or "Script pending" with the reason, and offers View, History and Regenerate.

Pipelines created before stored scripts generate their script on the first run after the upgrade and reuse it after that.

## Values withheld

When the server sets `DATRIS_AI_SAMPLE_VALUES=false`, the prompt carries the column names and schema types (or a value-free skeleton of a JSON or XML file) and the line "Sample rows withheld by configuration" instead of sample rows. The generated script still runs on the full data. If the transformation depends on what values look like, spell the format out in the instruction. See [Field Protection](/transformation/field-protection#what-still-sees-raw-data).

## Works with all file types

- **CSV/delimited files** — The script reads and writes CSV with the appropriate delimiter.
- **JSON files** — The script parses JSON, transforms records, and writes JSON.
- **XML files** — The script uses `xml.etree.ElementTree` to parse, transform, and write XML.

## CLI

```bash
datris ingest data.csv --dest postgres --ai-transform "convert dates to YYYY/MM/DD and uppercase all names"
```

## Requirements

- `ai.enabled: true` must be set in `application.yaml`
- The Vault secret for the AI provider must be configured (see [AI Configuration](/ai-configuration))
- `python3` must be available where the script runs: the `datris-codegen-runner` container on a compose install (`USE_CODEGEN_RUNNER=true`, the default), or the server itself when scripts run in-process (`USE_CODEGEN_RUNNER=false`)
