MCP Server

Datris includes a built-in Model Context Protocol (MCP) server that lets AI agents interact with the platform natively. Any MCP-compatible agent — Claude Desktop, Claude Code, Cursor, or custom agentic frameworks — can discover data, create pipelines, upload files, monitor jobs, search vector databases, query structured data, and answer questions with AI.

What AI Agents See

When an AI agent connects to Datris via MCP, it receives these instructions:

Datris is the first AI Agent-Native Data Platform. It ingests, validates, transforms, and routes data to databases, message queues, and vector stores — all driven by pipeline configurations that AI agents can create and manage programmatically.

A pipeline defines a complete data processing flow:

  • Source — file format (CSV, JSON, XML, PDF, Word, Excel, PowerPoint, HTML, Markdown, and more), schema with field names and types
  • Data Quality — header validation, AI-powered rules, and schema validation
  • Transformation — deduplication, trimming, and AI transforms
  • Preprocessor — optional REST endpoint called before processing
  • Destination — PostgreSQL, MongoDB, Kafka, ActiveMQ, REST endpoint, or vector databases (Qdrant, Weaviate, Milvus, Chroma, pgvector) with embedding configuration

Recommended Agent Workflow

1
Check what already exists call list_pipelines and list_taps first. If a pipeline already exists for this data, query it directly; if a tap exists, run or test it directly — don't re-create.
2
Discover the source (optional) if you don't know what's available, call discover_source with a natural-language question (e.g. "what datasets are in yfinance?"). Returns a structured catalog with tap instructions ready to build.
3
Create a pipeline (if needed) call create_pipeline with sample data — schema is auto-detected. Keep the config simple: source + destination only. Do not add dataQuality or transformation sections unless explicitly requested (use codegen_rule / codegen_transform for plain-English rules). create_pipeline upserts by name — calling it again with the same name replaces the config in place without dropping destination data, so you can edit a pipeline (add keyFields for dedupe, flip truncate, change codegen_rule) without delete-then-recreate.
4
Ingest data — Option A: direct upload call upload_data with base64-encoded content and the pipeline name. Then go to step 6 (verify).
5
Ingest data — Option B: create a tap taps pull data from external APIs, websites, or databases on demand or on a schedule. Five sub-steps:
5a
Create secrets (if needed) if the tap needs credentials (API keys, tokens), call list_tap_secrets first — reuse an existing secret by passing its name as secret_name to create_tap. Only create a new one (via create_tap_secret) when nothing existing fits. Use get_tap_secret_fields to confirm a candidate has the required keys (names only; values stay in Vault).
5b
Create the tap call create_tap with an instruction (AI generates the script — slower, 1-2 min) or with your own Python fetch() function (faster and more reliable). Pass secret_name to bind credentials from step 5a. Pass tap_type=document for PDFs/Word/HTML into a vector-store pipeline.
5c
Test the tap call test_tap to validate the script without pushing data. If it fails, fix the script and call create_tap again — repeat until test passes.
5d
Run the tap call run_tap and READ the response's persisted field before doing anything else. persisted: true → capture publisherToken and go to step 6. persisted: false → check persistedReason and act on it (no_target_pipeline, test_mode, run_error, no_records). Do NOT query the destination and report record counts from the response body — those records haven't landed yet.
5e
Schedule (optional) call update_tap with a cron_expression to run on a schedule. For each scheduled run, call get_tap_logs to pick up its publisherToken, then verify via step 6.
6
Verify ingestion landed Direct uploads (from step 4): call get_job_status and poll until COMPLETED or FAILED.
Tap runs (from step 5d or 5e): call get_pipeline_status(publisher_token=...) and poll until every row's state is end or error. The tap log only tells you the script ran; the publisher token is how you confirm records actually landed in the destination.
7
Query & search structured data: query_postgres, query_mongodb, or query_natural (plain-English → SQL). Vector/semantic: search_qdrant, search_pgvector, search_weaviate, search_milvus, search_chroma.
8
RAG combine search results with ai_answer for AI-powered question answering.
9
Manage call update_tap to enable/disable, change schedule, or retarget pipeline. Use get_tap to inspect details and the stored script. For document taps, get_tap_ledger shows which files have been processed (pass clear_uri or clear_all to force re-ingestion).
