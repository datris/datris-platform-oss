# Release Notes

## v1.52.0 — October 19, 2026

**The recovery agent shows its work: evidence before you approve, a rehearsal before anything lands, and a history of every script it touches.**

- **See what a fix will do before you approve it.** Incidents and their approvals show an evidence card: what the resource feeds, columns added and removed, rows and data-quality pass rate before and after, the biggest null-rate changes, each threshold with a pass or fail, and a link to compare the script before and after. Column values are never shown. The incident webhook now includes a one-line summary of the same numbers, with no values.
- **Fixes are rehearsed in a scratch lane before they land.** When the recovery agent proposes a fix for a failing tap, the platform first runs it against a scratch copy of the pipeline and compares the result with the last good run. A fix that clearly breaks the data is stopped with nothing written; one that changes the data's shape waits for a person, who can review the evidence and choose "Proceed to real run". Installs with the recovery agent in `propose` or `autopilot` will see one extra verification step per incident, and some proposals may now end as failed or waiting for a person on the evidence alone. Taps that fetch documents skip the rehearsal and are verified with the real run, as before. Set `recovery.verifyMode` to `real` in the agent policy to keep the previous behaviour for every tap. A rehearsal that passes counts as the fix's test run, so an approved fix can be saved on a scheduled tap; while the fix awaits approval, the tap's "Last test" shows the rehearsed fix, and the tap's own last test comes back if the fix is rejected.
- **Column changes, rejected credentials and platform problems are named for you.** When a scheduled tap run succeeds but its columns changed, an incident opens that names the added and removed columns and what is downstream; it is diagnosis-only unless you set `recovery.allowSchemaDriftActions` and run the tap on `autopilot`. A run that fails because the source rejected its credentials is marked as a credential problem, never retried or rewritten by the agent, and its card shows the name of the secret to check. A failure the doctor traces to the platform is marked as a platform problem with the doctor's fix, before any AI is used. While diagnosing, the agent can now also read lineage, provenance and pipeline version history.
- **Every AI script change is kept; compare and restore.** Each change to the script a pipeline runs for its AI data-quality rule or AI transformation (generated at save or at a run, regenerated, adopted from the code repository, or imported by a catalog restore) is now kept as a numbered version with its text. Open **Script history** on a pipeline's run page, or **History** beside the transformation script in the Lineage panel, to see who changed it and when, compare any two versions line by line, and restore one as the new live script with no model call; the pipeline's own version does not change. A version written for a different instruction or source schema than the pipeline has now is refused with the reason. Agents get the same through four new MCP tools. Scripts stored before this release appear as version 1 the first time their history is opened or they change.
- **Changing a pipeline's AI script now needs the right to update pipelines.** Regenerating a script, loading the latest version from the code repository and restoring a script version need `pipeline:update` instead of `pipeline:create`. The editor role and full-access keys are unaffected. Keys that hold `pipeline:create` but not `pipeline:update`, including keys made from the `rag-builder` template, can no longer regenerate or load scripts; add `pipeline:update` to any key that should. Under an agent policy, regenerating and restoring a script are the new `pipeline:update:codegen-scripts` action, which the Recommended template sends for approval.
- **The recovery agent can repair a failing AI script.** When a pipeline fails because its AI data-quality or transformation script fails, the recovery agent can regenerate that script from the pipeline's current instruction, within your agent policy. For a pipeline fed by a tap, the new script is proven in the scratch lane and then by a real run of the tap; if either fails, the previous script is restored. For a pipeline fed by uploads or other sources, the incident says plainly that the fix could not be verified and the next run will tell. The incident's card names the script versions before and after and opens their line-by-line comparison. Destination and schema problems still go to a person. The `recovery-agent` key gains the right to update pipelines the next time the server starts, recorded in the audit log; a revoked key is left alone.
- **Script fixes show up in a tap's history.** A script fix applied by the recovery agent, a script generated, fixed, reviewed or optimized with AI, or a script replaced through the API or the tap script editor, now appears in the tap's version history with who made it. A save that changes nothing records no version, even with a change note.
- **Recovery settings that fit the environment.** The Agent Policy page shows the recovery settings recommended for the install's `DATRIS_ENV` label next to the current ones, and an admin can apply them with one click: on `dev`, autopilot with looser limits (row-count changes up to 50 %, removed columns and type changes allowed); on `qa`, `production` or an unlabelled install, propose with the strict limits. The recovery mode never changes by itself and stays off until you set it. The new verification limits default the same way when you have not set them, so a `dev` install uses the looser limits and every other install the strict ones; saving the recovery settings fixes the values you see.
- **Choose the recovery mode on the Agent Policy page.** The Recovery panel now lets an admin pick off, propose or autopilot, choose scratch-first or real verification, and allow schema-drift fixes, with a one-line explanation of each choice; switching to autopilot asks for confirmation. Thresholds are shown there and still set through the API or the Configuration assistant.
- **The recovery agent learns source quirks, with your say-so.** When an incident is fixed by changing a tap's script and the agent noted a quirk of the source worth remembering, the note is saved as a suggested tap prompt fragment. It is not used until a person accepts it, after which the tap generator takes it into account for that source. Suggestions can be listed through the tap prompts API; agents can read them but cannot accept them.
- **An incident closes itself once the tap or pipeline runs healthy again.** An incident waiting on a person now closes as resolved when the tap or pipeline next runs healthy, whether you re-ran it after fixing the cause or its next scheduled run succeeded. Any actions it had queued for approval are withdrawn. Resolved incidents no longer hold off a new incident for the same tap or pipeline.
- **An incident that hits an error after an approval now closes right away.** If the recovery agent's work after an approved step fails with an error, the incident closes as failed with that error instead of waiting for the runtime limit.
